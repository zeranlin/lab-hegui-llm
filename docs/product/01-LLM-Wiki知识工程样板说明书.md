# LLM-Wiki 知识工程样板说明书

版本:: 1.0
状态:: 初稿
适用范围:: 政府采购招标文件合规审查知识系统
关联样板:: `lab-hegui-llm`

## 1. 文档目的

本文用于说明 `lab-hegui-llm` 项目的样板价值：它不是最终业务系统，也不是普通文档库，而是用 LLM + Wiki 方式验证政府采购招标文件合规审查知识如何被生产、组织、调用、复盘和回写。

公司关注 AI 时代知识库的价值，本样板要回答三个问题：

- 政府采购招标文件审查知识能否用更轻量的方式高效生产；
- 知识能否从静态资料变成可驱动 AI 审查动作的规则和经验；
- 人工复核后的漏报、误报和专家判断能否回流为可复用知识。

## 2. 为什么不是传统知识库

传统知识库通常解决“资料存在哪里”和“如何搜索”的问题，但政府采购招标文件合规审查需要解决的是“如何审、依据什么审、审完如何变准”。

传统方式的主要不足：

| 问题 | 表现 | 对审查的影响 |
| --- | --- | --- |
| 知识静态化 | 法规、案例、模板分别存放 | AI 和审查人员难以直接执行 |
| 更新成本高 | 结构严、流程重、维护慢 | 地方政策和业务经验难以及时沉淀 |
| 粒度不合适 | 多数停留在文档或条文级 | 难以形成可执行风险审查点 |
| 经验不可回流 | 人工修改留在项目里 | 同类问题下次仍然漏报或误报 |
| AI 调用不稳定 | 只做全文检索或问答 | 不能控制判断边界和输出口径 |

LLM + Wiki 的目标不是替代正式产品，而是在产品化之前，用低成本方式跑通知识工程闭环。

## 3. LLM + Wiki 模式的核心价值

LLM + Wiki 的价值在于把知识管理从“资料管理”推进到“动作管理”。

| 能力 | Wiki 承担 | LLM 承担 | 产品价值 |
| --- | --- | --- | --- |
| 知识沉淀 | 用 Markdown 保存法规、规则、案例、复盘 | 从非结构化材料中抽取知识 | 降低知识生产成本 |
| 知识组织 | 用目录、双链、索引组织关系 | 辅助归类、补全、生成摘要 | 快速形成领域知识地图 |
| 审查执行 | 用审查矩阵、风险点、模板约束动作 | 按知识执行画像、逐章审查、风险输出 | 让 AI 不再自由发挥 |
| 人工复盘 | 保存人工调整、漏报误报、知识申请 | 总结调整原因和可回写内容 | 让经验进入下一轮审查 |
| 快速迭代 | 直接修改 Markdown 和模板 | 批量生成或修订候选知识 | 在产品定型前快速试错 |

## 4. 样板中的知识工程闭环

当前样板已经形成一条可运行的知识闭环：

```text
原始法规/招标文件
  -> LLM 辅助抽取和整理
  -> Wiki 分层沉淀
  -> 文件画像和知识路由
  -> 逐章审查和风险输出
  -> 人工调整复盘
  -> 知识更新申请
  -> 回写知识层
```

其中，`wiki/10-法规依据/`、`wiki/20-知识点/`、`wiki/25-风险审查点/`、`wiki/40-审查工作台/`、`wiki/90-模板/` 分别承担不同层次的知识生产和审查执行职责。

## 5. 样板验证的不是界面，而是机制

`lab-hegui-llm` 当前最重要的价值不是前端界面，而是验证了正式产品需要具备的底层机制：

- 政府采购审查知识可以被分层管理；
- 文件画像可以作为知识路由器；
- 逐章审查矩阵可以作为审查调度器；
- 风险审查点可以作为 AI 判断的最小规则单元；
- 审查记录可以反链法规、知识点和原文证据；
- 人工调整可以通过复盘和知识更新申请进入闭环；
- 提示词可以把 Wiki 知识转成 AI 可执行动作。

## 6. 与正式产品的关系

LLM + Wiki 是知识生产和验证层，正式产品是知识治理和审查作业层。

| LLM + Wiki 样板 | 正式产品映射 |
| --- | --- |
| Markdown 目录 | 产品模块和知识分类 |
| Wiki 元数据 | 知识条目字段 |
| Obsidian 双链 | 对象关系和知识图谱 |
| 审查记录模板 | 审查任务表单 |
| 人工复盘模板 | 质量提升工作台 |
| 知识更新申请 | 知识发布审批流 |
| 风险审查点页面 | 规则库和审查点库 |
| 提示词页面 | AI 审查编排配置 |

正式产品不应简单复制 Wiki 页面，而应把样板中已经验证有效的机制产品化、结构化和流程化。

## 7. 样板成功标准

本样板是否成功，不看页面数量，而看以下标准：

- 是否能定义什么是政府采购招标文件审查知识；
- 是否能用知识驱动文件画像、知识路由、逐章审查和风险输出；
- 是否能让每个风险有原文、依据、审查点和修改建议；
- 是否能通过人工复盘识别漏报、误报和知识缺口；
- 是否能把复盘结论转成知识更新申请；
- 是否能证明下一份同类文件审查受益于前一次复盘。

## 8. 产品经理判断

本样板已经验证了政府采购招标文件合规审查可以采用 LLM + Wiki 的方式进行知识工程建设。它的定位不是最终交付系统，而是正式产品的知识内核样板和作业机制样板。

下一步应将 Wiki 中已经稳定的知识层、审查动作、复盘机制和回写机制，抽象为正式产品中的数据对象、状态流、权限模型、任务引擎和质量指标。
