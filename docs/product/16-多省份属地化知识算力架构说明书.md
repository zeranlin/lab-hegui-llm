# 多省份属地化知识算力架构说明书

版本:: 1.0
状态:: 初稿
适用范围:: 政府采购招标文件合规审查知识作业平台

## 1. 文档目的

本文用于说明产品如何支持多省份、多品类、本地条款、本地算力和 LLM + Wiki 知识生产模式。

产品不能设计成传统统一 SaaS 后台，也不能让所有地区共用一套不可区分的知识和模型。政府采购具有明显属地化特征，不同省份可能需要不同知识、不同品类、不同部署方式和不同算力资源。

## 2. 核心设计原则

### 2.1 全国共性和地方差异分开

全国通用规则作为基础知识包，各省份在此基础上叠加本地知识包。

```text
全国通用知识包
  + 省份知识包
  + 市级或平台知识包
  + 品类审查包
  + 本地复盘知识
```

### 2.2 知识和算力按租户隔离

不同省份或客户可以绑定不同知识空间和算力环境。

示例：

```text
福建租户
  -> 福建知识空间
  -> 福建算力环境
  -> 福建启用品类：物业管理
```

```text
四川租户
  -> 四川知识空间
  -> 四川算力环境
  -> 四川启用品类：计算机设备
```

### 2.3 品类包可独立上线

每个省份不必一次性上线所有品类。产品应支持按省份、按品类逐步启用。

例如：

- 福建先上线物业管理；
- 四川先上线计算机设备；
- 广东后续上线医疗设备；
- 某市只上线信息化设备和物业服务。

### 2.4 LLM + Wiki 用于知识生产，产品用于稳定运行

LLM + Wiki 继续作为知识生产、复盘和验证工具；正式产品承接已复核知识的发布、调用、权限和指标。

## 3. 总体架构

```text
LLM + Wiki 知识生产层
  -> 知识审核发布层
  -> 省份知识空间
  -> 品类审查包
  -> AI 审查编排层
  -> 本地算力环境
  -> 审查工作台
  -> 人工复盘和知识回写
```

## 4. 知识空间设计

### 4.1 全国知识空间

存放全国通用的政府采购规则：

- 政府采购法律法规；
- 财政部规章和规范性文件；
- 通用采购方式规则；
- 通用风险审查点；
- 通用输出口径；
- 通用品类基础规则。

全国知识空间可以被各省继承，但地方规则不能反向污染全国规则。

### 4.2 省份知识空间

每个省份建立独立知识空间：

- 福建知识空间；
- 四川知识空间；
- 广东知识空间；
- 深圳知识空间；
- 其他省市知识空间。

省份知识空间包括：

- 本省法规政策；
- 本省平台规则；
- 本省集采目录和限额标准；
- 本省审查口径；
- 本省人工复盘；
- 本省试运行规则。

### 4.3 平台知识空间

针对特定交易平台、集采平台或电子采购系统建立平台规则。

平台规则主要处理：

- 电子投标材料；
- 格式要求；
- 信用信息调用；
- 平台证明材料；
- 操作流程；
- 模板限制。

平台规则不能突破上位法，不得单独创设限制供应商的实体条件。

## 5. 品类审查包设计

品类审查包独立于省份，但上线时与省份知识空间组合。

### 5.1 物业管理审查包

重点风险：

- 人员年龄、性别、身高、形象限制；
- 本地化服务要求；
- 同类业绩限定过窄；
- 人员证书堆叠；
- 方案类主观分档；
- 合同考核、扣款、付款、验收。

### 5.2 计算机设备审查包

重点风险：

- 技术参数指向特定品牌或型号；
- 软硬件兼容性要求不合理；
- 制造商授权或售后承诺函要求不当；
- 国产化和安全要求适用不清；
- 评分因素与采购需求脱节；
- 节能环保政策落实不足。

### 5.3 信息化设备和系统集成审查包

重点风险：

- 软件著作权异常加分；
- 等保、密评、信创要求适用边界；
- 本地服务网点；
- 售后响应时限；
- 技术参数排他性；
- 运维和验收标准不清。

## 6. 本地算力设计

### 6.1 算力环境类型

产品应支持：

- 公司统一云算力；
- 省份专属云算力；
- 客户本地私有化算力；
- 政务云算力；
- 混合算力。

### 6.2 算力绑定规则

每个租户绑定默认算力环境：

| 租户 | 知识空间 | 算力环境 | 启用品类 |
| --- | --- | --- | --- |
| 福建租户 | 福建知识空间 | 福建算力 | 物业管理 |
| 四川租户 | 四川知识空间 | 四川算力 | 计算机设备 |
| 深圳租户 | 深圳知识空间 | 深圳算力 | 物业管理、信息化设备 |

### 6.3 数据隔离

要求：

- 招标文件不得跨租户访问；
- 省份复盘数据默认不跨省共享；
- 本地知识默认只在本省生效；
- 全国通用知识由统一复核后下发；
- 跨省知识借鉴必须走引入和复核流程。

## 7. LLM + Wiki 协同模式

### 7.1 省份 Wiki

每个省份可维护独立 Wiki：

```text
wiki/福建/
  -> 法规依据
  -> 品类审查包
  -> 审查记录
  -> 人工复盘
  -> 知识更新申请
```

也可在当前 Wiki 结构中通过元数据管理省份。

### 7.2 知识生产流程

```text
地方法规/招标文件/人工复盘
  -> LLM 辅助抽取
  -> Wiki 草稿
  -> 专家复核
  -> 知识更新申请
  -> 正式产品发布
  -> AI 审查调用
```

### 7.3 Wiki 到产品同步

同步对象：

- 法规条目；
- 审查知识点；
- 风险审查点；
- 品类审查包；
- 语料样本；
- 提示词；
- 知识更新申请。

同步前必须完成：

- 元数据完整性检查；
- 适用地域确认；
- 品类边界确认；
- 状态确认；
- 版本生成。

## 8. 省份上线流程

```text
省份立项
  -> 确定上线品类
  -> 初始化全国知识继承
  -> 采集地方条款
  -> 建立省份知识空间
  -> 配置本地算力
  -> 导入样本文件
  -> LLM + Wiki 生成样板知识
  -> 专家复核
  -> 试运行
  -> 正式上线
  -> 持续复盘
```

## 9. 示例一：福建上线物业品目

配置：

- 租户：福建；
- 知识空间：福建知识空间；
- 算力：福建算力；
- 启用品类：物业管理；
- 继承知识：全国通用政府采购规则；
- 本地知识：福建法规、福建平台规则、福建物业复盘样本。

审查链路：

```text
福建物业招标文件
  -> 福建算力解析
  -> 识别为福建 + 物业管理
  -> 调用全国规则 + 福建规则 + 物业审查包
  -> 输出风险
  -> 福建审查人员复核
  -> 福建物业知识回写
```

## 10. 示例二：四川上线计算机品目

配置：

- 租户：四川；
- 知识空间：四川知识空间；
- 算力：四川算力；
- 启用品类：计算机设备；
- 继承知识：全国通用政府采购规则；
- 本地知识：四川法规、四川平台规则、四川计算机设备复盘样本。

审查链路：

```text
四川计算机设备招标文件
  -> 四川算力解析
  -> 识别为四川 + 计算机设备
  -> 调用全国规则 + 四川规则 + 计算机设备审查包
  -> 重点检查技术参数、品牌型号、节能环保、售后授权
  -> 人工复核
  -> 四川计算机品类知识回写
```

## 11. 跨省知识复用机制

跨省复用不能直接复制，应采用“候选引入”机制：

```text
福建物业规则
  -> 作为候选知识推荐给四川
  -> 四川地域复核人判断是否适用
  -> 适用则进入四川试运行
  -> 验证后转有效
```

复用类型：

- 全国通用规则：可统一下发；
- 品类经验：可候选引入；
- 地方规则：默认不可跨省直接使用；
- 平台规则：仅对应平台使用；
- 人工复盘：需脱敏和复核后使用。

## 12. 关键产品能力

- 租户管理；
- 省份知识空间；
- 品类包启用配置；
- 算力环境绑定；
- 全国知识继承；
- 本地知识隔离；
- 跨省候选引入；
- Wiki 到产品发布；
- 本地复盘回写；
- 省份和品类指标看板。

## 13. 关键指标

- 省份知识包初始化完成率；
- 品类包上线数量；
- 本地知识命中率；
- 全国知识命中率；
- 跨省误用拦截次数；
- 本地算力调用成功率；
- 本地文件解析成功率；
- 省份 AI 风险确认率；
- 省份漏报率；
- 省份误报率；
- 本地知识回写采纳率。

## 14. 产品经理结论

多省份属地化不是部署细节，而是本产品的核心业务架构。政府采购行业天然要求“全国规则打底、地方规则落地、品类规则审查、本地算力运行、人工复盘回写”。

因此正式产品必须从第一期就按“省份知识空间 + 品类审查包 + 本地算力 + LLM-Wiki 知识生产层”的方式设计，避免做成传统通用平台后再被动改造。
