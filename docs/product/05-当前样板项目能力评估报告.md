# 当前样板项目能力评估报告

版本:: 1.0
状态:: 初稿
评估对象:: `lab-hegui-llm`
评估范围:: 政府采购招标文件合规审查 LLM + Wiki 样板

## 1. 评估结论

`lab-hegui-llm` 已经具备“知识驱动政府采购招标文件合规审查”的样板雏形。它不是普通 demo，也不是最终产品，而是一个用于验证 LLM + Wiki 知识工程模式的可运行知识原型。

当前项目已经验证：

- 可以用 Wiki 分层组织政府采购审查知识；
- 可以将法规、知识点、风险审查点、语料、提示词和审查记录连接起来；
- 可以用文件画像、知识路由、逐章审查矩阵驱动 AI 审查动作；
- 可以通过人工调整复盘和知识更新申请形成闭环；
- 物业管理品类已经有较完整的样板路径。

但它还不是正式产品系统，主要缺少结构化数据模型、流程引擎、权限、版本、状态审批、审查任务调度和质量指标看板。

## 2. 已具备能力

### 2.1 知识分层能力

当前项目已形成较清晰的知识目录：

| 层级 | 当前目录 | 说明 |
| --- | --- | --- |
| 法规依据 | `wiki/10-法规依据/` | 存放政府采购法律、规章、政策和地方规则 |
| 行业基础 | `wiki/15-行业基础/` | 存放采购方式、文件结构、行业概览和场景画像 |
| 审查知识点 | `wiki/20-知识点/` | 存放资格、评分、合同、政策等审查知识 |
| 风险审查点 | `wiki/25-风险审查点/` | 存放可执行风险规则 |
| 风险库 | `wiki/30-风险库/` | 存放跨项目风险模式 |
| 审查工作台 | `wiki/40-审查工作台/` | 存放项目审查记录、复盘和知识申请 |
| 语料摘录 | `wiki/50-语料与摘录/` | 存放真实招标文件摘录 |
| 提示词 | `wiki/60-提示词/` | 存放画像、抽取、审查提示词 |
| 模板 | `wiki/90-模板/` | 存放审查记录、复盘、知识更新模板 |

该结构基本符合政府采购行业知识从权威依据到审查动作再到项目复盘的分层逻辑。

### 2.2 知识动作化能力

项目中已有 `动作型知识系统建设纲领`，明确提出稳定知识必须回答：

```text
看哪里、找什么、怎么判断、怎么输出、怎么回写。
```

这是区别于传统法规库和普通知识库的关键能力。

当前样板已经将知识用于：

- 文件画像；
- 知识路由；
- 逐章审查；
- 风险判断；
- 风险输出；
- 人工复盘；
- 知识回写。

### 2.3 政府采购行业适配能力

当前项目没有做成通用文档审查，而是围绕政府采购招标文件审查展开。

已覆盖的政府采购特性包括：

- 法规层级；
- 地方规则；
- 采购方式；
- 品目和场景；
- 招标文件章节；
- 资格条件；
- 采购需求；
- 评审办法；
- 政府采购政策；
- 合同履约；
- 质疑投诉视角；
- 风险证据链。

这说明项目方向符合“政府采购行业专用产品”，不是泛文档 AI 工具。

### 2.4 审查主流程样板能力

README 和审查模板中已经定义了待审文件处理流程：

```text
原始文件入库
  -> 文本抽取
  -> 来源笔记
  -> 文件画像
  -> 逐章审查
  -> 风险清单
  -> 审查记录
```

项目中已有物业管理和信息化设备样本，物业管理已形成更完整的样板闭环。

### 2.5 人工复盘和知识回写能力

项目中已有：

- 人工调整复盘模板；
- 审查精确率复盘模板；
- 知识更新申请模板；
- 物业管理人工调整复盘样本；
- 物业管理知识更新申请样本。

这说明项目已经不是一次性 AI 审查，而是开始形成“AI 审查 -> 人工修正 -> 知识回写”的质量提升路径。

## 3. 当前不足

### 3.1 仍以文档形态为主

当前 Wiki 页面虽然有元数据，但整体仍是 Markdown 文档，不是正式产品里的结构化对象。

正式产品需要将以下内容对象化：

- 知识条目；
- 法规依据；
- 风险审查点；
- 招标文件；
- 文件章节；
- 项目画像；
- 审查任务；
- 风险项；
- 人工反馈；
- 知识更新申请；
- 规则版本。

### 3.2 缺少产品级状态流

当前 Wiki 中有草稿、有效、试运行等状态表达，但还不是系统状态流。

正式产品需要支持：

- 状态变更权限；
- 审批动作；
- 状态变更日志；
- 生效时间；
- 失效时间；
- 回滚机制；
- 试运行观察。

### 3.3 缺少权限和角色隔离

当前样板通过文档说明角色，但没有产品级权限。

正式产品需要区分：

- 知识维护人；
- 业务审查人；
- 品类专家；
- 法规复核人；
- 地域复核人；
- 知识管理员；
- 系统管理员。

### 3.4 缺少审查任务引擎

当前审查流程主要靠 Markdown 模板和人工执行。

正式产品需要任务引擎支持：

- 文件上传；
- 解析任务；
- 画像任务；
- 分章审查任务；
- 风险聚合任务；
- 报告生成任务；
- 失败重试；
- 任务状态追踪。

### 3.5 缺少质量指标

当前有复盘意识，但缺少可量化指标。

正式产品需要跟踪：

- AI 风险准确率；
- 漏报率；
- 误报率；
- 人工修改率；
- 风险等级调整率；
- 原文定位准确率；
- 知识命中有效率；
- 知识回写采纳率；
- 单份文件审查耗时。

当前样板最值得保留并产品化的机制：

- 知识分层目录；
- 文件画像作为知识路由器；
- 逐章审查矩阵；
- 风险审查点作为最小规则单元；
- 风险输出证据链；
- 人工调整复盘；
- 知识更新申请；
- 物业管理品类动作包；
- 提示词驱动的 AI 审查编排。

## 6. 产品经理结论

`lab-hegui-llm` 已经证明“LLM + Wiki 管理政府采购招标文件审查知识”是可行的。它适合作为正式产品的知识工程样板和业务机制原型。

下一阶段不应简单继续堆文档，而应围绕样板中已经跑通的机制做产品化抽象：

- 把 Wiki 页面抽象为产品对象；
- 把模板抽象为表单；
- 把双链抽象为对象关系；
- 把审查记录抽象为审查任务；
- 把复盘记录抽象为质量提升流程；
- 把知识更新申请抽象为审批流；
- 把提示词抽象为 AI 编排配置；
- 把样板结果抽象为可衡量指标。
