# 政府采购招标文件审查协议

类型:: 审查协议
状态:: 试运行
主题:: 政府采购招标文件; AI 审查; 调度协议
适用阶段:: 业务审查主流程
适用范围:: 政府采购货物和服务招标文件合规审查
关联纲领:: [[wiki/00-入口/动作型知识系统建设纲领]]
关联知识点:: [[wiki/20-知识点/政府采购招标文件画像]]; [[wiki/20-知识点/知识分层与路由规则]]; [[wiki/20-知识点/政府采购逐章审查矩阵]]
关联模板:: [[wiki/90-模板/审查记录模板]]; [[wiki/90-模板/AI调度运行记录模板]]

## 1. 定位

本协议是 AI 执行政府采购招标文件合规审查时必须遵守的动作契约。

知识点负责解释判断逻辑，风险审查点负责定义风险规则，审查协议负责规定 AI 必须按什么顺序读取、抽取、判断、拆分、校验和输出。执行器读取 wiki 时，不能只检索相似知识后自由总结，必须把本协议转化为本次审查任务包。

## 2. 总体链路

```text
新文件入库
  -> 建立文件画像
  -> 执行知识路由
  -> 生成本次审查动作任务包
  -> 按章节读取原文
  -> 逐项执行审查动作
  -> 拆分原子风险
  -> 校验证据链
  -> 质量门反查漏项
  -> 输出审查记录和运行记录
  -> 生成知识更新申请或人工调整复盘入口
```

## 3. 强制输入

每次审查至少读取以下内容：

- 待审招标文件原文或已抽取纯文本；
- [[wiki/20-知识点/政府采购招标文件画像]]；
- [[wiki/20-知识点/知识分层与路由规则]]；
- [[wiki/20-知识点/政府采购逐章审查矩阵]]；
- 本次画像命中的品类动作协议；
- 本次画像或章节信号命中的横向专题动作协议；
- 本次画像命中的风险审查点；
- [[wiki/70-审查协议/风险原子化规则]]；
- [[wiki/70-审查协议/质量门规则]]；
- [[wiki/90-模板/审查记录模板]]；
- [[wiki/90-模板/AI调度运行记录模板]]。

## 4. 文件画像动作

AI 必须先形成文件画像，不得跳过画像直接输出风险。

画像至少包括：

- 项目编号、项目名称、采购人、代理机构；
- 适用地域、采购方式、评审方法；
- 采购品目、采购标的、标的属性、所属行业；
- 预算金额、最高限价、分项预算、采购计划编号；
- 是否专门面向中小企业、是否接受联合体、是否允许分包、是否允许进口产品；
- 主要章节完整性，包括公告、资格、用户需求、评分办法、合同、投标文件格式；
- 初步风险入口，包括缺失字段、异常证书、异常评分、人员限制、合同空白、模板错配。

画像输出后，必须记录本次调用的通用规则、地域规则、采购方式规则、品类规则、场景规则和章节规则。

## 5. 动作任务包

执行器必须把路由结果转换为动作任务包。每个动作任务至少包含：

| 字段 | 要求 |
| --- | --- |
| 动作ID | 稳定编号，便于运行记录和质量门追踪 |
| 动作名称 | 用审查人员能理解的业务名称 |
| 必读章节/原文范围 | 不能只写“全文”，应列明公告、需求、评分、合同等 |
| 触发信号 | 命中关键词、缺失字段、章节结构或画像标签 |
| 必须检查 | 明确要判断的成立条件和排除条件 |
| 执行状态 | 命中、未命中、待确认 |
| 命中风险候选 | 命中时列出候选风险标题 |
| 未命中说明 | 未发现风险时说明已查范围和不成立原因 |
| 关联审查点 | 链接到 `wiki/25-风险审查点/` |
| 是否需要人工复核 | 是或否，并说明原因 |

## 6. 逐章执行规则

AI 必须按章节推进，不能只依据关键词命中。

最低章节顺序为：

1. 招标公告和项目基本信息；
2. 采购计划、预算、报价和标的明细；
3. 政府采购政策和中小企业声明函；
4. 资格条件、联合体、分包和分公司授权；
5. 投标人须知、资格性审查表、符合性审查表；
6. 用户需求书，包括服务范围、人员、设备、费用、响应、验收；
7. 评分办法，包括价格、技术、商务、诚信和证明材料；
8. 投标文件格式，包括承诺函、偏离表、声明函和证明材料要求；
9. 合同条款，包括服务范围、付款、验收、违约、保密和模板残留；
10. 质疑投诉视角复核，包括模糊、矛盾、排他、不可复核条款。

每章必须形成“已审查结论”。未发现风险也要记录执行状态，避免漏审后无法追踪。

评分办法章节必须单独反查财务类商务评分：凡出现财务情况、财务审计报告、银行资信证明、资产负债表、利润表、现金流量表、营业收入、纳税额、资产规模、银行授信等触发信号，应调用 [[wiki/25-风险审查点/财务指标或财务报告作为评分项不当]] 判断是否成立风险；不成立时也应说明是否属于资格核验、特殊履约需要或未设置评分差异。

采购需求、技术要求、样品要求和证明材料章节必须单独反查技术要求横向专题：凡出现技术参数、`▲`、`★`、标准号、现行标准、强制标准、检测报告、CMA、CNAS、委托单位、报告日期、样品照片、实验过程照片、未检出、抗菌抗病毒、样品结构尺寸或中标后深化等触发信号，应调用 [[wiki/70-审查协议/技术要求合规性审查动作协议]]，并形成重要参数清单、标准引用清单、检测报告清单、样品要求清单和未列风险说明。

## 7. 风险生成规则

风险成立必须同时具备：

- 招标文件原文证据或明确缺失事实；
- 对应风险审查点或知识点；
- 成立理由和排除条件判断；
- 对采购竞争、政策适用、评审公正、履约执行或合同管理的影响；
- 可执行的修改建议。

`原文内容` 字段只能放招标文件原文摘录。风险理由、解释、推理和建议必须放入 `问题说明`、`审查依据` 或 `修改建议`。

## 8. 证据链校验

输出前必须逐条检查：

- 原文位置是否能回到文件章节、行号、页码或条款；
- 原文内容是否为原文，不是 AI 改写；
- 风险标题是否指向具体条款和问题；
- 关联审查点是否真实存在；
- 法规依据不确定时是否标记 `需进一步确认`；
- 修改建议是否能被采购人或代理机构直接执行。

## 9. 运行记录

每次审查必须形成运行记录，至少记录：

- 审查日期和具体时间；
- 输入文件和知识库路径；
- 本次读取的知识、协议、风险审查点和原文范围；
- AI 调度轮次；
- 每轮输入目标、读取范围、中间产物和输出摘要；
- 动作任务包执行情况；
- 质量门检查结果；
- 未列风险说明；
- 是否使用外部参考。标准 AI 审查不得使用外部 V2、标准答案或人工批注反推。

## 10. 权限边界

执行器对本项目 wiki 的默认权限应为只读加产物写入：

- 可读：`raw/`、`wiki/10-法规依据/`、`wiki/15-行业基础/`、`wiki/20-知识点/`、`wiki/25-风险审查点/`、`wiki/30-风险库/`、`wiki/60-提示词/`、`wiki/70-审查协议/`、`wiki/90-模板/`；
- 可写：`wiki/40-审查工作台/审查记录/`、`wiki/40-审查工作台/运行记录/`、`wiki/40-审查工作台/知识更新申请/`、`wiki/40-审查工作台/人工调整复盘/`；
- 禁止自动改写：法规依据、稳定知识点、风险审查点、风险库、审查协议；
- 需要人工确认后回写：可复用漏报、误报边界、品类动作、质量门规则。

## 11. 对执行器的最低要求

如果执行器要复现本 wiki 的 AI 审查能力，至少需要支持：

- 读取本协议并生成结构化动作任务包；
- 跟踪每个动作的执行状态；
- 强制输出未命中动作说明；
- 按 [[wiki/70-审查协议/风险原子化规则]] 拆分风险；
- 按 [[wiki/70-审查协议/质量门规则]] 反查漏项；
- 把动作执行表、风险清单和质量门结果写入运行记录。
