# 知识驱动审查执行规范

类型:: 审查协议
状态:: 试运行
主题:: 知识驱动; 审查执行; 方法规范
适用对象:: 可读取本 LLM Wiki 的 AI、人工审查人、自动化执行主体
适用阶段:: 新文件审查; 审查复核; 流程复现
关联纲领:: [[wiki/00-入口/动作型知识系统建设纲领]]
关联总协议:: [[wiki/70-审查协议/政府采购招标文件审查协议]]
关联动作协议:: [[wiki/70-审查协议/物业管理审查动作协议]]
关联质量门:: [[wiki/70-审查协议/质量门规则]]

## 1. 定位

本规范说明：任何外部执行主体如何读取本 LLM Wiki，并按照同一套政府采购招标文件合规审查方法执行。

这里的“执行主体”可以是 Codex、其他大模型 Agent、脚本系统、业务平台或人工审查人。本文不绑定任何具体工程项目、命令名称或实现方式，只定义知识系统对外提供的方法、流程、规范和可复现要求。

本知识库的职责是提供：

- 政府采购行业知识；
- 法规依据和风险审查点；
- 文件画像方法；
- 知识路由规则；
- 逐章审查矩阵；
- 品类动作协议；
- 风险原子化规则；
- 质量门；
- 审查记录和运行记录模板；
- 审后复盘和知识回写方法。

外部执行主体的职责是读取这些知识，并把知识转成自己的执行流程。外部执行主体不应要求本知识库为某个具体工具生成项目化开发任务。

## 2. 知识读取顺序

外部执行主体审查新文件时，应按以下顺序读取知识：

```text
AGENTS.md
  -> wiki/index.md
  -> wiki/00-入口/动作型知识系统建设纲领
  -> wiki/20-知识点/政府采购招标文件画像
  -> wiki/20-知识点/知识分层与路由规则
  -> wiki/20-知识点/政府采购逐章审查矩阵
  -> wiki/70-审查协议/政府采购招标文件审查协议
  -> 品类动作协议
  -> 风险原子化规则
  -> 质量门规则
  -> 审查记录和运行记录模板
```

如果文件画像命中物业管理，应额外读取：

- [[wiki/15-行业基础/物业管理服务采购背景]]
- [[wiki/20-知识点/物业管理动作化审查包]]
- [[wiki/70-审查协议/物业管理审查动作协议]]
- 与画像命中的场景对应的风险审查点和知识点。

## 3. 执行链路

知识驱动审查不是“检索几条知识后让模型自由总结”，而是以下链路：

```text
读取原文
  -> 建立文件画像
  -> 根据画像路由知识
  -> 生成本次审查动作清单
  -> 按章节和动作读取原文
  -> 对每个动作形成命中/未命中/待确认
  -> 将命中项拆成原子风险
  -> 补足原文证据和审查依据
  -> 执行质量门反查
  -> 生成审查记录
  -> 生成运行记录
  -> 将可复用漏报误报进入复盘和知识更新流程
```

## 4. 文件画像要求

文件画像是知识路由的前置动作。外部执行主体不得跳过画像直接输出风险。

画像至少包括：

| 维度 | 必填内容 |
| --- | --- |
| 基本信息 | 项目编号、项目名称、采购人、代理机构 |
| 程序属性 | 采购方式、评审方法、是否评定分离、提交投标截止时间 |
| 标的属性 | 采购品目、采购标的、数量、单位、标的所属行业 |
| 金额信息 | 预算金额、最高限价、分项预算、采购计划编号 |
| 政策适用 | 中小企业、节能环保、进口产品、绿色采购、核心产品 |
| 组织规则 | 联合体、分包、分公司、关联主体、资格条件 |
| 文件结构 | 公告、须知、资格、需求、评分、合同、格式是否完整 |
| 场景标签 | 学校物业、医院物业、法院机关物业、信息化设备等 |
| 初步入口 | 缺失项、异常人员、异常证书、异常评分、合同空白 |

画像输出必须反向说明：本次为什么调用某些知识点、风险审查点和动作协议。

## 5. 知识路由要求

知识路由应按层级执行：

```text
全国通用规则
  -> 地方规则
  -> 采购方式规则
  -> 标的属性规则
  -> 品类规则
  -> 场景规则
  -> 章节规则
  -> 试运行规则
```

外部执行主体应记录本次调用的知识清单。记录内容至少包括：

- 调用的法规依据；
- 调用的行业基础；
- 调用的知识点；
- 调用的风险审查点；
- 调用的审查协议；
- 调用的模板；
- 未调用但可能相关的知识及原因。

## 6. 动作清单生成

动作清单来自审查协议和品类动作协议，不由外部执行主体凭经验临时编造。

动作清单至少包含：

| 字段 | 要求 |
| --- | --- |
| 动作ID | 来自动作协议，例如 `PROP-A09` |
| 动作名称 | 与动作协议一致 |
| 必读章节 | 明确原文范围 |
| 触发信号 | 关键词、缺失字段、章节结构或画像标签 |
| 必须检查 | 成立条件和排除条件 |
| 执行状态 | 命中、未命中、待确认 |
| 命中风险 | 对应风险标题或候选 |
| 未命中说明 | 已读范围和不成立原因 |
| 关联审查点 | 对应 `wiki/25-风险审查点/` |
| 人工复核 | 是否需要人工确认 |

物业管理项目应从 [[wiki/70-审查协议/物业管理审查动作协议]] 生成 `PROP-A01` 至 `PROP-A23` 的动作清单。

## 7. 原文读取要求

外部执行主体必须按章节和动作读取原文，不得只读摘要或只按关键词命中。

最低读取范围：

- 招标公告；
- 采购计划、预算和服务需求明细；
- 政府采购政策和声明函；
- 资格条件、联合体、分包、分公司；
- 资格性审查和符合性审查；
- 用户需求书；
- 评分办法；
- 证明材料和投标文件格式；
- 合同条款；
- 付款、验收、违约和考核条款。

读取结果应能支持原文定位，优先保留行号、页码、条款号或表格位置。

## 8. 风险判断要求

风险成立不得只靠模型感觉。每条风险至少满足：

- 有原文证据或明确缺失事实；
- 有关联风险审查点；
- 有风险成立理由；
- 有排除条件判断；
- 有法规、知识点或审查协议依据；
- 有可执行修改建议；
- 能被人工单独确认、驳回、降级、合并或拆分。

法律依据不确定时，标记为 `需进一步确认`，不得强行定性。

## 9. 风险原子化要求

外部执行主体必须按 [[wiki/70-审查协议/风险原子化规则]] 拆分风险。

特别注意以下不得合并：

- 人员证书组合和人员社保时点；
- 人员证书组合和证明材料负担；
- 需求端年龄形象限制和评分端人员证书限制；
- 体系认证范围和供应商资质等级证书；
- 同类业绩范围和业绩证明材料；
- 合同模板错配和付款、验收、违约空白；
- 响应度评分、承诺函评分和方案类主观分档。

如果外部执行主体选择合并风险，必须说明合并理由，并保证合并后仍能分别整改。

## 10. 输出字段要求

每条风险至少包含：

```text
风险标题
结论类型
风险等级
原文位置
原文内容
问题说明
关联动作ID
关联审查点
审查依据
修改建议
是否需要人工复核
```

字段边界：

- `原文内容` 只放招标文件原文；
- `问题说明` 放判断理由；
- `关联动作ID` 放动作协议中的动作编号；
- `关联审查点` 放稳定风险审查点；
- `修改建议` 放可执行修订动作。

## 11. 质量门要求

外部执行主体输出前必须执行 [[wiki/70-审查协议/质量门规则]]。

最低质量门：

- 文件画像是否完整；
- 知识路由是否完整；
- 动作清单是否全部有状态；
- 每条风险是否有原文证据；
- 每条风险是否有关联动作ID和审查点；
- 是否存在应拆未拆的风险；
- 人员评分是否反查证书、社保、证明材料；
- 供应商能力评分是否反查认证、资质、业绩、荣誉、软著；
- 用户需求是否反查人员限制、校外边界、响应时限；
- 合同条款是否反查模板错配、付款、验收、违约；
- 风险数量异常偏低时是否触发漏项反查。

质量门结果应写入运行记录。

## 12. 运行记录要求

运行记录用于证明审查过程可追溯、可复现。

运行记录至少包含：

- 审查日期和具体时间；
- 输入文件；
- 使用的知识库路径；
- 调用知识清单；
- 文件画像；
- 动作清单及执行状态；
- 逐章读取范围；
- 风险原子化检查；
- 质量门结果；
- 未命中动作说明；
- 待人工复核事项；
- 是否使用外部参考；
- 是否修改知识库。

## 13. 权限边界

外部执行主体读取本知识库时，应遵守：

- `raw/` 原始文件只读；
- 稳定法规、知识点、风险审查点、风险库、审查协议只读；
- 审查产物写入项目审查记录或外部系统自己的输出目录；
- 审后发现的可复用漏报误报，应进入人工复盘和知识更新申请流程；
- 不得把外部标准答案、人工批注或 V2 检查结果混入标准 AI 审查口径。

## 14. 复现目标

一个外部执行主体如果正确读取并执行本知识系统，应能复现 Codex 审查的主要方法：

- 不是只检索关键词；
- 不是只输出大类风险；
- 会先画像和路由；
- 会逐章读取；
- 会按动作协议执行；
- 会拆分原子风险；
- 会用质量门反查漏项；
- 会记录未命中动作；
- 会保留原文证据；
- 会把审查结论反链到知识。

这就是本知识系统对外提供的核心能力。
