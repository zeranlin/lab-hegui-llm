状态:: 有效

适用范围:: 政府采购招标文件合规审查
关联设计:: [[wiki/00-入口/四线闭环知识系统设计]]
关联流程:: [[wiki/00-入口/审查动作系统]]; [[wiki/20-知识点/政府采购招标文件画像]]; [[wiki/20-知识点/知识分层与路由规则]]; [[wiki/20-知识点/政府采购逐章审查矩阵]]

## 1. 纲领目标

建设一个可由 AI 调度执行的政府采购行业招标文件审查动作型知识系统。

系统的核心目标不是保存更多资料，而是让知识能够直接参与政府采购招标文件合规审查动作：

```text
每一条稳定知识，都必须能回答：
看哪里、找什么、怎么判断、怎么输出、怎么回写。
```

只有能影响文件画像、逐章审查、风险判断、结果输出或知识回写的内容，才是本系统中的有效知识。

当前系统定位是“AI 调度执行”，不是 raw 目录自动监听和无人值守自动审查。新招标文件进入后，需要 AI 按本知识系统完成文本抽取、来源笔记、文件画像、知识路由、逐章审查、审查记录生成和 lint 校验；高风险结论和知识回写仍需人工复核。

## 2. 核心原则

### 2.1 知识必须动作化

每个知识点、风险审查点、语料样本和提示词都要服务审查动作。

不能只写：

- 这是什么；
- 法规怎么说；
- 可能存在风险。

必须写清：

- 审查人要看哪个章节；
- 原文中要找哪些信号；
- 什么条件下构成风险；
- 什么条件下不构成风险；
- 审查记录中如何表达；
- 发现漏报或误报后回写到哪里。

### 2.2 文件画像是路由器

文件画像不是摘要，而是决定调用哪些知识的路由器。

画像至少要识别：

- 地域；
- 采购方式；
- 文件类型；
- 采购品目；
- 标的属性；
- 所属行业；
- 评审方法；
- 采购场景；
- 政策适用；
- 平台或地方规则。

画像完成后，应能决定本项目调用哪些法规、行业画像、逐章矩阵、风险审查点、语料样本和提示词。

### 2.3 逐章审查矩阵是调度器

逐章审查矩阵不是文件结构说明，而是审查动作调度表。

每个章节必须定义：

- 输入内容：本章通常包含哪些原文；
- 必查字段：必须识别哪些信息；
- 缺失项：应写但未写的内容；
- 触发审查点：本章可能触发哪些风险审查点；
- 输出字段：审查记录中应写到哪里。

### 2.4 风险审查点是最小规则单元

`wiki/25-风险审查点/` 是 AI 审查的最小稳定规则单元。

每个风险审查点必须包含：

- 适用范围；
- 地域和品类边界；
- 审查章节；
- 识别信号；
- 判断规则；
- 排除条件；
- 常见误报；
- 典型原文；
- 输出口径；
- 修改建议；
- 回写规则。

### 2.5 项目结果必须反链知识

每个项目风险点都必须能反查到：

- 文件画像标签；
- 原文位置；
- 逐章审查章节；
- 风险审查点；
- 法规或知识依据；
- 缺失类规则；
- 人工调整记录；
- 知识更新申请。

如果一个风险点无法关联稳定审查点，应先标记为“待归类风险”，再通过复盘判断是否新增知识。

## 3. 动作化知识单元标准

每条稳定知识应按以下结构建设：

| 字段 | 要回答的问题 |
| --- | --- |
| 适用范围 | 哪些地域、采购方式、品类、场景适用 |
| 审查章节 | 应该看招标文件哪个章节 |
| 审查动作 | 审查人下一步具体做什么 |
| 识别信号 | 原文中出现什么内容会触发检查 |
| 缺失信号 | 应有内容未出现时如何判断 |
| 判断规则 | 风险成立的条件是什么 |
| 排除条件 | 什么情况下不作为风险 |
| 常见误报 | AI 容易误判的位置 |
| 输出口径 | 风险标题、问题说明、修改建议怎么写 |
| 回写位置 | 漏报或误报后应更新哪个知识层 |

## 4. 三个关键组件

### 4.1 画像路由规则

画像路由规则要把项目属性映射到知识调用。

示例：

```text
地域=深圳市
品类=物业管理
采购方式=公开招标
标的属性=服务
场景=学校物业
评标方法=综合评分法
  -> 调用国家政府采购通用规则
  -> 调用深圳地方政府采购规则
  -> 调用服务类公开招标规则
  -> 调用物业管理专项画像
  -> 调用学校物业场景风险
  -> 调用评分办法、人员证书、合同履约、付款验收审查点
```

### 4.2 逐章调度矩阵

逐章调度矩阵要把章节映射到审查点。

示例：

| 章节 | 必查内容 | 触发审查点 | 输出位置 |
| --- | --- | --- | --- |
| 招标公告 | 项目名称、预算、采购方式、资格要求、联合体 | 资格条件违法或过度；采购方式适用错误 | 文件画像；风险点清单 |
| 采购需求 | 服务范围、人员配置、技术服务要求、验收要求 | 采购需求不完整不明确；技术参数或服务要求指向特定供应商 | 逐章审查记录；风险点清单 |
| 评分办法 | 分值结构、人员证书、业绩、认证、主观分档 | 人员学历职称证书异常加分；同类业绩限定过窄；方案类评分主观裁量过大 | 风险点清单 |
| 合同条款 | 付款、验收、违约、服务期、费用边界 | 合同关键空白或模板错配；付款方式和支付时限不明确 | 风险点清单；待确认 |

### 4.3 风险输出规范

风险输出必须让审查人员直接使用。

每个风险点必须包含：

- 风险标题；
- 结论类型；
- 风险等级；
- 原文位置；
- 原文内容；
- 问题说明；
- 关联审查点；
- 审查依据；
- 修改建议。

其中：

- `原文内容` 只放招标文件原文，不写解释；
- `问题说明` 写风险判断理由；
- `关联审查点` 连接稳定规则；
- `修改建议` 给出可执行修订方向。

## 5. 建设路径

### 5.1 第一阶段：物业管理样板

先以政府采购行业物业管理招标文件合规性审查作为首个动作化样板。

目标：

- 物业管理招标文件画像规则完整；
- 物业管理逐章审查矩阵完整；
- 物业管理常见风险审查点标准化；
- 5 份物业管理招标文件 AI 审查记录全部能反链到审查点；
- 人工调整复盘能生成知识更新申请；
- 更新后的知识能影响下一份政府采购物业管理招标文件审查。

### 5.2 第二阶段：信息化设备扩展

在物业样板稳定后，扩展到信息化设备。

重点补充：

- 技术参数指向性；
- 品牌、型号、专利、软著；
- 制造商授权；
- 售后服务和本地化；
- 节能环保和绿色采购；
- 系统集成、运维、兼容性和验收标准。

### 5.3 第三阶段：跨地域规则化

在品类样板稳定后，补充地域化规则。

重点补充：

- 全国通用规则；
- 广东省规则；
- 深圳市规则；
- 平台规则；
- 地域冲突处理；
- 地域有效、地域待核和地域废止状态。

### 5.4 第四阶段：效果评估和持续回写

通过真实项目持续评估：

- 召回率；
- 准确率；
- 原文定位准确率；
- 规则归因率；
- 人工调整率；
- 知识更新闭环率。

每次复盘都必须说明更新了哪一层知识。

## 6. 当前优先动作

当前阶段不继续扩大资料规模，优先把已有知识动作化。

优先顺序：

1. 选择 `物业管理` 作为首个样板品类。
2. 将物业相关风险审查点改造成动作卡片。
3. 将 [[wiki/20-知识点/政府采购逐章审查矩阵]] 改造成“章节 -> 审查点 -> 输出字段”的调度矩阵。
4. 将 [[wiki/20-知识点/政府采购招标文件画像]] 和 [[wiki/20-知识点/知识分层与路由规则]] 改造成“画像标签 -> 调用知识”的路由规则。
5. 回查 5 份物业 AI 审查记录，确认每个风险是否都有稳定审查点支撑。
6. 形成 `物业管理动作化审查包`。

## 7. 完成标准

当一个品类满足以下条件时，才算完成动作化：

- 新文件进入后，系统能先画像，再自动确定审查范围；
- 逐章审查能触发明确审查点；
- 风险输出能给出原文、理由、依据和建议；
- 缺失类风险能被单独识别；
- 人工调整能进入复盘；
- 可复用调整能生成知识更新申请；
- 更新后的知识能影响下一份文件审查。

达到以上标准，才是真正的“一个可由 AI 调度执行的政府采购行业招标文件审查动作型知识系统”。
