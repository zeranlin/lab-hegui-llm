## 1. 最终目标

建设一个面向政府采购招标文件合规审查的 AI 知识系统。系统不仅保存资料，还要能管理知识、驱动审查、承接人工修正，把修正结果回写为可复用知识，并让外部业务执行器、AI Agent、脚本系统或人工审查助理能够读取本知识库后复现同一套审查动作。

具体建设应遵循 [[wiki/00-入口/动作型知识系统建设纲领]]：每一条稳定知识都必须能回答“看哪里、找什么、怎么判断、怎么输出、怎么回写”。

最终系统由四条线组成。其中前三条线构成本知识库内部治理和业务审查闭环，第四条线负责把知识系统开放给外部执行主体使用。

```text
知识生成管理层
  -> 业务审查主流程
  -> 审后调整和精确率提升层
  -> 知识生成管理层

外部执行主体使用线
  -> 读取知识系统
  -> 初始化审查动作
  -> 复现业务审查主流程
  -> 输出 AI 审查记录和运行记录
```

四条线的关系是：

- 知识生成管理层决定“系统知道什么、能用什么、谁能改什么”。
- 业务审查主流程决定“收到文件后如何审、如何输出结果”。
- 审后调整和精确率提升层决定“业务人员如何改结果、如何沉淀为新知识”。
- 外部执行主体使用线决定“外部系统如何读懂本知识库、如何按同一套动作复现审查过程、如何输出可审计结果”。

第四条线不是某个具体执行器的开发任务，也不是本知识库去维护外部工程代码。它只沉淀方法、协议、读取顺序、动作约束、质量门和复现路径，让不同执行主体能够按照统一知识口径完成政府采购招标文件合规审查。

## 2. 什么是知识

本系统中的知识不是泛泛的资料，而是能够影响 AI 审查动作、判断边界或输出结果的稳定内容。

一条内容只有满足至少一个条件，才进入知识库：

- 能帮助识别招标文件属于什么采购场景；
- 能决定某类条款是否构成风险；
- 能解释某个风险为什么成立或为什么不成立；
- 能指导 AI 从哪个章节、字段或原文信号中查找问题；
- 能作为法规、政策、案例、原文样本或审查经验被复用；
- 能降低漏报、误报或表述不清。

不进入稳定知识库的内容：

- 单个项目的临时判断；
- 没有依据的经验性结论；
- 尚未复核的外部标注；
- 只适用于某一份文件且不能复用的措辞修改；
- 与政府采购合规审查无关的背景材料。

## 3. 什么是政府采购行业知识

政府采购行业知识是围绕“采购文件是否合法、合理、完整、可执行”形成的专业判断体系。

它至少包括八类：

| 知识类型 | 说明 | 当前落点 |
| --- | --- | --- |
| 法规依据 | 法律、行政法规、部门规章、地方规则、财政规范性文件 | `wiki/10-法规依据/` |
| 行业基础 | 政府采购主体、采购方式、品目、政策功能、招标文件结构 | `wiki/15-行业基础/` |
| 审查动作 | 文件画像、逐章审查、缺失项检查、证据链要求 | `wiki/00-入口/`; `wiki/20-知识点/` |
| 判断规则 | 某类条款如何判断风险、如何排除误报 | `wiki/20-知识点/`; `wiki/25-风险审查点/` |
| 风险模式 | 可复用风险类型，如本地化限制、业绩过窄、评分脱节 | `wiki/30-风险库/` |
| 场景画像 | 物业、信息化设备、医院、法院、学校等专项场景风险入口 | `wiki/15-行业基础/` |
| 语料样本 | 招标文件原文、典型问题条款、正常条款和边界样本 | `wiki/50-语料与摘录/` |
| 操作提示词 | 画像、抽取、审查、复盘、回写知识的提示词 | `wiki/60-提示词/` |

## 4. 知识分层

知识库分为七层。越靠上越稳定，越靠下越贴近业务项目。

### 4.1 法规层

位置：`wiki/10-法规依据/`

作用：

- 提供权威依据；
- 支撑风险判断；
- 支撑人工复核和质疑投诉应对。

建设要求：

- 保留法规来源和本地原文路径；
- 逐步拆解为条文级审查规则；
- 区分国家规则、深圳地方规则、专项政策。

### 4.2 行业基础层

位置：`wiki/15-行业基础/`

作用：

- 解释政府采购行业的基本概念；
- 定义采购方式、品目、政策功能、文件结构；
- 提供细分场景画像。

建设要求：

- 每个采购品类形成“场景画像”；
- 每个画像必须写明常见章节、常见风险入口、容易误判的位置。

### 4.3 通用知识点层

位置：`wiki/20-知识点/`

作用：

- 把法规和行业经验转成审查动作；
- 定义逐章审查矩阵、缺失类风险、采购需求和评分闭环。

建设要求：

- 每个知识点要能回答“审查人下一步看什么”；
- 不只写概念，要写检查项、触发信号、输出字段。

### 4.4 风险审查点层

位置：`wiki/25-风险审查点/`

作用：

- 作为项目风险识别的最小稳定规则单元；
- 连接原文、风险标题、判断理由、法规依据和修改建议。

每个风险审查点至少包括：

- 适用范围；
- 识别信号；
- 判断规则；
- 排除条件；
- 常见原文；
- 常见误报；
- 关联法规或知识点；
- 推荐修改方向。

### 4.5 风险模式层

位置：`wiki/30-风险库/`

作用：

- 管理跨品类、跨项目反复出现的风险模式；
- 帮助 AI 从模式上归类和表达风险。

风险模式不替代风险审查点。风险模式偏“类”，风险审查点偏“审查规则”。

### 4.6 项目工作层

位置：`wiki/40-审查工作台/`

作用：

- 存放具体项目的 AI 审查记录；
- 保留项目画像、风险点、原文内容、问题说明和修改建议。

要求：

- 审查记录目录必须和 `raw/招标文件/` 分类一致；
- 项目审查记录只记录当前项目结论，不直接承载稳定知识；
- 项目中发现的新规则，必须通过复盘或知识更新流程进入稳定知识层。

### 4.7 语料和提示词层

位置：`wiki/50-语料与摘录/`; `wiki/60-提示词/`

作用：

- 语料层保存典型原文和边界样本；
- 提示词层把知识系统转为 AI 可执行任务。

要求：

- 原文样本必须保留来源；
- 提示词必须明确输入、输出、禁止事项和质量标准。

## 5. 知识状态、地域适用和权限

知识条目必须同时有状态和适用范围。政府采购审查不能只判断一条知识“是否有效”，还要判断它在国家、省、市、采购平台、采购方式和品类场景中是否适用。

原因是：

- 国家法律、行政法规、财政部规章具有全国通用效力；
- 省级财政部门可能有本省执行口径、电子交易平台规则和模板要求；
- 同一省份内，不同城市可能有本地条例、实施细则、负面清单、集中采购目录、限额标准和平台操作规则；
- 深圳等地方还可能存在特区条例、地方实施细则、供应商信用规则等本地专门规则；
- 同一规则在货物、服务、工程、框架协议、合作创新、物业管理、信息化设备等场景中的适用边界不同。

因此，知识条目的最小元数据建议包括：

```text
状态::
效力层级:: 国家/省级/市级/区县/平台/项目
适用地域:: 全国/广东省/深圳市/其他
适用采购方式::
适用品目或场景::
依据来源::
生效日期::
失效日期::
复核人::
复核日期::
权限级别::
```

### 5.1 通用状态

| 状态 | 含义 | 是否可驱动正式审查 |
| --- | --- | --- |
| 草稿 | 初步整理，未经复核 | 否 |
| 待复核 | 已形成规则，但依据或边界未确认 | 谨慎使用，只能提示 |
| 有效 | 已复核，可用于正式审查 | 是 |
| 试运行 | 新增规则，需用若干项目观察误报和漏报 | 可以使用，但需标记 |
| 废止 | 已被法规、规则或经验替代 | 否 |

### 5.2 地域适用状态

同一知识在不同地域可以有不同状态。状态不能简单全局继承。

| 地域状态 | 含义 | 审查使用方式 |
| --- | --- | --- |
| 全国有效 | 国家层面规则，未发现地方冲突 | 可作为基础规则使用 |
| 本省有效 | 省级规则或经省级口径确认 | 仅在该省项目中使用 |
| 本市有效 | 市级规则、地方条例、平台口径或集中采购规则 | 仅在该市项目中使用 |
| 平台有效 | 交易平台或集采机构模板规则 | 仅在对应平台或集采项目中使用 |
| 地域待核 | 规则可能适用，但尚未确认本地口径 | 只能作为提示，不作为确定风险 |
| 地域冲突 | 上位法、本地规则或平台规则存在不一致 | 必须人工复核，不自动下结论 |
| 地域废止 | 本地规则已失效或被新规则替代 | 不使用 |

示例：

- “不得以不合理条件限制或排斥供应商”属于全国有效基础规则。
- “深圳供应商信用信息、诚信评分或平台操作要求”只能标记为深圳市或对应平台有效。
- 某省集中采购目录、限额标准、电子交易平台材料格式要求，只能在该省或平台有效。
- 同一省不同城市存在本地采购条例或平台模板差异时，应分别建地域适用口径，不能混用。

### 5.3 规则冲突处理

当规则存在层级或地域冲突时，按以下顺序处理：

1. 先识别项目地域、采购人层级、采购方式、采购平台和采购品目。
2. 优先适用上位法的强制性规定。
3. 地方规则不得突破上位法的禁止性规定。
4. 地方规则可以补充程序、模板、信用、平台操作和目录限额等本地口径。
5. 平台规则只能作为操作和材料提交口径，不能单独创设限制供应商的实体条件。
6. 无法判断冲突时，项目审查记录中标记“需人工复核”，不直接定性为明确违规。

### 5.4 权限模型

权限按角色和地域共同管理：

| 角色 | 权限 |
| --- | --- |
| 知识维护人 | 新增草稿、整理语料、补充来源，不得直接将规则标记为有效 |
| 业务审查人 | 使用本项目地域内有效知识审查项目，提出知识更新建议 |
| 地域复核人 | 复核某省、市或平台规则，将地域待核规则升为本地有效、退回或废止 |
| 法规复核人 | 复核国家层面和上位法规则，处理上位法与地方规则冲突 |
| 品类专家 | 复核物业、信息化设备、医疗、工程等品类专项规则 |
| 系统管理员 | 管理目录、模板、脚本、状态规则和 lint 规则 |

权限使用原则：

- 全国规则的有效状态应由法规复核人确认；
- 省、市、平台规则的有效状态应由对应地域复核人确认；
- 品类专项规则应由品类专家或具备该品类经验的复核人确认；
- 业务审查人可以提出知识更新申请，但不直接把项目个案写成有效规则；
- 系统管理员管理结构和流程，不替代业务复核。

当前本地 wiki 可先用文档状态和元数据模拟权限。后续如果接入系统，再把 `状态::`、`效力层级::`、`适用地域::`、`权限级别::` 和角色映射到真实权限。

## 6. 第一条线：知识生成管理层

知识生成管理层处理“知识从哪里来、怎么进入、如何变成可用规则”。

### 6.1 知识来源

- 法规和政策文件；
- 政府采购品目目录和政策标准；
- 历史招标文件；
- 业务审查经验；
- 质疑投诉、行政处罚、监督检查结果；
- 人工复核和专家意见；
- AI 审查中的漏报、误报和不确定项。

### 6.2 知识入库流程

```text
来源材料
  -> 来源笔记
  -> 初步摘录
  -> 知识归类
  -> 规则化
  -> 复核
  -> 标记有效
  -> 进入审查动作系统
```

### 6.3 规则化标准

一条知识要能驱动审查，必须从“描述性内容”变成“动作性规则”。

规则化时必须回答：

- 查哪个章节；
- 找哪些原文信号；
- 什么情况下构成风险；
- 什么情况下不构成风险；
- 输出时应归入哪个风险审查点；
- 应引用什么依据；
- 给什么修改建议。

## 7. 第二条线：业务审查主流程

业务审查主流程处理“新文件来了怎么审”。

主流程保持现有设计：

```text
招标文件入库
  -> 文本抽取
  -> 来源笔记
  -> 文件画像
  -> 逐章审查
  -> 风险审查点匹配
  -> AI 审查记录
```

主流程输出的是项目结果，不是知识沉淀。

项目审查记录必须做到：

- 文件画像完整；
- 风险点能定位原文；
- `原文内容` 只放文件原文；
- `问题说明` 写判断理由；
- 每个风险点关联稳定审查点；
- 对缺失类风险说明“应有内容”和“未见内容”。

## 8. 第三条线：审后调整和精确率提升层

审后调整层处理“业务人员如何改 AI 结果，以及改完是否更新知识”。

### 8.1 人工调整类型

| 调整类型 | 说明 | 是否需要回写知识 |
| --- | --- | --- |
| 补充漏报 | AI 未识别但人工认为存在风险 | 通常需要 |
| 删除误报 | AI 识别为风险但人工认为不成立 | 通常需要 |
| 修改风险等级 | 风险成立但严重程度不准 | 视情况需要 |
| 修改风险标题 | 风险成立但表达不专业 | 视情况需要 |
| 修改原文定位 | 风险成立但原文摘录不准 | 通常需要补语料 |
| 修改建议优化 | 风险成立但整改建议不落地 | 视情况需要 |
| 项目特殊判断 | 因项目背景导致例外 | 不一定，先作为项目备注 |

### 8.2 调整后的分流

人工调整不能只停留在项目记录里。调整后必须分流：

```text
人工调整
  -> 是否属于可复用问题？
    -> 是：知识更新申请
    -> 否：仅保留项目审查备注
```

可复用问题包括：

- 同类文件可能反复出现；
- 影响风险成立或不成立；
- 暴露了现有审查点缺失；
- 暴露了现有审查点误报边界不清；
- 暴露了提示词没有要求检查；
- 暴露了文件画像或逐章矩阵缺项。

## 9. 第四条线：外部执行主体使用线

外部执行主体使用线处理“别人如何使用本知识库完成同样的审查”。

这里的外部执行主体包括：

- AI Agent；
- 自动化执行器；
- 脚本系统；
- 业务平台；
- 人工审查助理。

这条线不关心外部系统使用什么编程语言、命令名称、模型供应商或工程目录。它只关心外部执行主体是否能读取本知识库，并按本知识库定义的政府采购招标文件审查动作执行。

- [[wiki/70-审查协议/质量门规则]]
- [[wiki/90-模板/审查记录模板]]
- [[wiki/90-模板/AI调度运行记录模板]]

### 9.2 外部执行主体必须复现的动作

外部执行主体不能只做关键词检索或自由总结，必须复现以下动作：

```text
读取原文
  -> 建立文件画像
  -> 根据画像路由知识
  -> 生成动作清单
  -> 逐章逐动作审查
  -> 形成命中/未命中/待确认状态
  -> 拆分原子风险
  -> 补齐原文证据、问题说明、审查依据和修改建议
  -> 执行质量门反查
  -> 输出 AI 审查记录
  -> 输出运行记录
```

如果外部执行主体只输出风险清单，但没有画像、动作清单、质量门和运行记录，应视为没有完整使用本知识系统。

### 9.3 外部执行主体产物

外部执行主体完成审查后，应输出：

| 产物 | 作用 |
| --- | --- |
| 文件画像 | 证明本次审查路由正确 |
| 动作清单 | 证明逐章逐动作执行，而不是自由总结 |
| AI 审查记录 | 给业务审查人员查看和修改 |
| 运行记录 | 记录读取知识、执行轮次、中间产物和质量门结果 |
| 待确认清单 | 标记依据不明、原文不清或需要人工判断的问题 |

### 9.4 边界

外部执行主体使用线只提供知识和方法，不替外部工程做项目管理。

本知识库不产出面向某个具体执行器的开发任务、交接清单或代码修改要求。外部系统需要自行读取这些知识，并把知识转成自己的实现逻辑。

## 10. 精确率提升如何回写知识

精确率提升不是简单修改提示词，而是按归因回写到对应层。

| 问题 | 回写位置 |
| --- | --- |
| 法规依据缺失 | `wiki/10-法规依据/` |
| 场景背景不足 | `wiki/15-行业基础/` |
| 审查动作缺失 | `wiki/20-知识点/政府采购逐章审查矩阵.md` |
| 缺失类风险没查 | `wiki/20-知识点/缺失类风险审查.md` |
| 风险规则没有 | `wiki/25-风险审查点/` |
| 风险模式表达不清 | `wiki/30-风险库/` |
| 原文信号不足 | `wiki/50-语料与摘录/` |
| 提示词没约束 | `wiki/60-提示词/` |
| 输出结构不适合人工 | `wiki/90-模板/` |

回写后不能直接认为系统变准，必须进入下一轮项目验证。

## 11. 闭环质量指标

系统至少跟踪四类质量指标：

| 指标 | 说明 |
| --- | --- |
| 召回率 | 应识别风险中 AI 识别了多少 |
| 准确率 | AI 识别风险中人工认可多少 |
| 原文定位准确率 | 原文内容是否准确对应风险 |
| 规则归因率 | 风险点是否能关联到稳定审查点 |

在当前 wiki 阶段，可以先以人工复盘表记录这些指标，不急于自动计算。

## 12. 当前建设优先级

### 第一优先级：补齐知识治理总纲

- 固定知识定义、知识分层、状态和权限；
- 明确什么内容能进入稳定知识库；
- 明确项目结果和稳定知识的边界。

### 第二优先级：把风险审查点规则化

- 为每个风险审查点补齐识别信号、判断规则、排除条件、常见误报；
- 让审查点真正成为 AI 审查的最小规则单元。

### 第三优先级：建立人工调整和知识更新模板

- 使用 [[wiki/90-模板/人工调整复盘模板]] 记录业务人员如何调整 AI 审查结果；
- 使用 [[wiki/90-模板/知识更新申请模板]] 将可复用调整申请回写为稳定知识；
- 防止把单个项目意见直接污染稳定知识库。

### 第四优先级：条文级法规规则化

- 将核心法规逐条拆成审查动作；
- 形成“法规条文 -> 审查问题 -> 风险审查点”的映射。

### 第五优先级：品类专项化

- 先做物业管理和信息化设备；
- 每个品类形成专项画像、专项风险审查点和典型原文样本。

### 第六优先级：外部执行主体使用线标准化

- 固定外部执行主体读取知识的入口和顺序；
- 固定初始化成功标准；
- 固定动作清单、质量门和运行记录要求；
- 用真实项目运行记录校验外部执行主体是否复现了业务审查主流程。

## 13. 关键原则

- 知识先治理，再驱动审查。
- 项目结果不是稳定知识，必须经过复盘和复核才能回写。
- AI 审查输出必须服务人工审查，不追求炫技表达。
- 原文、判断、依据、建议必须分字段保存。
- 外部标注和人工意见可以提高系统，但不能直接替代 AI 审查主流程。
- 每一次精确率提升，都必须能说明它更新了哪一层知识。
- 外部执行主体只能读取和复现本知识库定义的方法，不应把本知识库变成某个执行器项目的开发管理仓库。
