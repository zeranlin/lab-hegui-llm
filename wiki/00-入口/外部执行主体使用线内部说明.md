## 1. 这条线解决什么问题

外部执行主体使用线解决的是：一个不在本仓库内部工作的执行主体，收到一份政府采购招标文件后，如何读懂 `lab-hegui-llm`，并按照同一套知识、动作和质量门完成审查。

这里的外部执行主体可以是：

- AI Agent；
- 自动化执行器；
- 脚本系统；
- 业务平台；
- 人工审查助理；
- 未来封装的命令行工具或审查服务。

这条线不关心某个外部工程怎么写代码，也不为某个具体工具生成开发任务。它只回答：

- 从哪里进入知识库；
- 先读哪些知识；
- 如何判断输入文件属于什么主题、品类和场景；
- 如何从画像路由到知识；
- 如何生成动作清单；
- 如何逐动作读取原文；
- 如何把候选问题拆成风险；
- 如何通过质量门；
- 如何输出 AI 审查记录和运行记录。

一句话：外部执行主体使用线是 `lab-hegui-llm` 面向外部执行者的“审查操作说明书”和“执行接口契约”。

## 2. 入口协议是什么

入口协议是 [[wiki/00-入口/外部执行主体招标文件审查指引]]。

外部执行主体只要接入本知识库，第一步必须读取这个入口协议。入口协议定义了：

| 协议内容    | 作用                                                                   |
| ------- | -------------------------------------------------------------------- |
| 定位      | 告诉执行主体本任务是政府采购招标文件合规性审查，不是摘要、问答或自由分析                                 |
| 必读知识顺序  | 告诉执行主体启动时必须读取哪些知识页                                                   |
| 标准流水线   | 固定 `文件画像 -> 知识路由 -> 动作清单 -> 逐动作执行 -> 风险原子化 -> 质量门反查 -> 报告生成 -> 运行记录` |
| 中间产物    | 要求每一步留下可审计产物，证明不是直接总结                                                |
| 画像字段    | 固定政府采购招标文件必须抽取的业务字段                                                  |
| 知识路由    | 根据地域、采购方式、品目、场景、章节命中知识                                               |
| 动作清单    | 将知识转成必须执行的检查动作                                                       |
| 逐动作执行   | 规定每个动作必须记录命中、未命中、待确认或不适用                                             |
| 风险原子化   | 规定风险必须拆成审查人员可单独理解和整改的问题                                              |
| 质量门     | 输出前反查漏项、误报、证据缺失和字段不合格                                                |
| 报告输出    | 固定 AI 审查记录和运行记录的字段                                                   |
| 禁止事项    | 防止外部执行主体使用标准答案、跳过画像、只靠关键词或无证据输出                                      |
| 初始化成功标准 | 判断外部执行主体是否真正接入了本知识库                                                  |

入口协议不是建议性说明，而是外部执行主体使用本知识库时必须遵守的执行契约。

## 3. 执行主体收到文件后的总流程

外部执行主体收到一份新招标文件后，完整执行过程如下：

```text
1. 接收文件
   -> 确认文件是否属于政府采购采购文件
   -> 抽取可读取文本和章节结构

2. 读取入口协议
   -> AGENTS.md
   -> wiki/index
   -> 外部执行主体招标文件审查指引

3. 建立文件画像
   -> 抽取项目、程序、金额、品目、政策、组织规则、章节、场景
   -> 形成 01-文件画像

4. 知识路由
   -> 全国通用规则
   -> 地方规则
   -> 采购方式规则
   -> 标的属性规则
   -> 品类规则
   -> 场景规则
   -> 章节规则
   -> 风险审查点
   -> 模板和质量门
   -> 形成 02-知识路由表

5. 生成动作清单
   -> 通用逐章矩阵
   -> 通用审查协议
   -> 命中品类动作协议
   -> 命中场景风险审查点
   -> 形成 03-动作清单

6. 逐动作执行
   -> 按动作读取原文
   -> 记录命中、未命中、待确认、不适用
   -> 形成 04-动作执行记录

7. 风险原子化
   -> 将候选问题拆成独立风险
   -> 关联动作ID、审查点、依据和原文
   -> 形成 05-原子风险清单

8. 质量门反查
   -> 查画像、路由、动作、证据、原文内容、风险拆分、缺失项
   -> 形成 06-质量门检查表

9. 输出结果
   -> 生成 07-AI审查记录
   -> 生成 08-运行记录
```

任何一步缺失，都不能视为完整执行了“政府采购行业招标文件审查”。

## 5. 画像到底要做什么

画像不是项目摘要。画像是知识路由的依据。

执行主体必须先回答：

```text
这是不是政府采购文件？
这是什么采购方式？
这是什么评审方法？
采购标的是什么？
标的属性和所属行业是什么？
适用哪个地域规则？
是否命中某个品类场景？
有哪些关键章节？
哪些字段缺失或异常？
哪些风险入口需要后续动作检查？
```

### 5.1 画像字段

`01-文件画像` 至少包括：

```text
项目编号::
项目名称::
采购人::
代理机构::
采购方式::
评审方法::
预算金额::
最高限价::
采购品目::
采购标的::
标的属性::
标的所属行业::
适用地域::
交易平台::
是否专门面向中小企业::
是否接受联合体::
是否允许分包::
是否允许进口产品::
场景标签::
文件章节清单::
初步风险入口::
画像置信度::
待确认项::
```

### 5.2 主题和场景识别

执行主体需要把文件映射到本知识库的主题和场景。

| 识别维度 | 示例 | 影响 |
| --- | --- | --- |
| 行业主题 | 政府采购招标文件合规审查 | 决定必须使用政府采购法规、政策和审查协议 |
| 采购方式 | 公开招标、竞争性磋商、谈判、询价 | 决定程序规则、评分方法和文件结构检查 |
| 地域 | 全国、广东、深圳、区级平台 | 决定地方规则是否适用 |
| 品目 | 物业管理、信息化设备、服务类、货物类 | 决定品类知识和动作协议 |
| 场景 | 学校物业、医院物业、法院机关物业 | 决定专项风险入口 |
| 章节 | 公告、需求、评分、合同、格式 | 决定逐章审查动作 |
| 风险主题 | 资格限制、人员评分、合同空白、中小企业政策 | 决定风险审查点调用 |

### 5.3 画像失败怎么处理

如果无法识别关键字段：

- 不得编造；
- 字段写 `未见` 或 `待确认`；
- 将缺失字段本身作为缺失类风险入口；
- 先按通用审查协议执行；
- 不得强行套用品类动作协议。

## 6. 知识路由到底怎么做

知识路由是把画像结果转成“本次该读哪些知识”。

固定顺序如下：

```text
全国通用规则
  -> 地方规则
  -> 采购方式规则
  -> 标的属性规则
  -> 品类规则
  -> 场景规则
  -> 章节规则
  -> 风险审查点
  -> 输出模板和质量门
```

### 6.1 路由表字段

`02-知识路由表` 至少包括：

```text
画像字段
命中规则
调用知识页
调用原因
适用层级
适用地域
适用品类或场景
是否必读
执行状态
未调用原因
```

### 6.2 物业管理示例

如果画像显示：

```text
采购品目:: 物业管理服务
标的属性:: 服务
适用地域:: 深圳
场景标签:: 学校物业 / 医院物业 / 法院机关物业
采购方式:: 公开招标
```

则至少应路由：

- 全国通用法规：政府采购法、实施条例、87号令、需求管理办法、中小企业办法；
- 深圳地方规则：深圳经济特区政府采购条例、实施细则、供应商信用信息管理办法；
- 通用知识：画像、逐章矩阵、缺失类风险、采购需求与评审因素闭环；
- 物业知识：物业管理服务采购背景、物业管理动作化审查包；
- 物业动作协议：`PROP-A01` 至 `PROP-A23`；
- 风险审查点：人员学历职称证书异常加分、供应商认证资质证书异常加分、体系认证范围特定化、同类业绩限定过窄、方案类评分主观裁量过大、合同关键空白或模板错配等；
- 输出模板：审查记录模板、AI调度运行记录模板；
- 质量门：逐章覆盖、动作完整、风险原子化、异常低风险数量反查。

## 7. 动作清单到底怎么生成

动作清单不是执行主体自由生成的待办。动作必须来自知识页：

- 通用逐章矩阵；
- 通用审查协议；
- 命中品类动作协议；
- 命中场景风险审查点；
- 缺失类风险审查规则；
- 质量门要求。

`03-动作清单` 至少包括：

```text
动作ID
动作名称
来源知识
必读章节
触发信号
必须检查
预期输出
关联风险审查点
是否必做
执行状态
未执行原因
```

动作清单要覆盖两类问题：

| 问题类型 | 说明 |
| --- | --- |
| 存在型风险 | 文件中写了某些内容，经判断构成风险，例如人员证书组合加分、本地服务时限、特定业绩等 |
| 缺失型风险 | 文件应当写明但未写明，例如预算金额、标的所属行业、付款方式、验收标准等 |

## 8. 逐动作执行到底怎么记录

每个动作都必须有结果，不能只记录发现风险的动作。

`04-动作执行记录` 至少包括：

```text
动作ID
动作名称
执行状态：命中 / 未命中 / 待确认 / 不适用
读取章节
读取范围
原文位置
原文摘录
命中信号
初步判断
关联审查点
是否形成候选风险
待确认原因
```

执行状态含义：

| 状态 | 含义 |
| --- | --- |
| 命中 | 已发现原文内容或缺失事实，并可能形成候选风险 |
| 未命中 | 已读取对应范围，未发现触发信号 |
| 待确认 | 原文不完整、依据不明确或需要人工判断 |
| 不适用 | 因采购方式、品类、场景不适用该动作 |

没有风险的章节，也要记录已读范围和未命中说明。这是防止漏报的关键。

## 9. 风险原子化怎么执行

执行主体不得把多个问题写成一条“大风险”。风险必须能被审查人员逐条阅读、逐条修改、逐条复核。

`05-原子风险清单` 至少包括：

```text
风险ID
来源动作ID
风险标题
结论类型
风险等级
原文位置
原文内容
问题说明
关联审查点
审查依据
修改建议
是否需人工复核
合并或拆分说明
```

字段边界必须遵守：

- `原文内容` 只放招标文件原文；
- `问题说明` 写为什么构成风险；
- `来源动作ID` 说明是哪个动作发现；
- `关联审查点` 指向 `wiki/25-风险审查点/`；
- `审查依据` 放法规、知识点、风险模式或协议；
- `修改建议` 写可执行的改法。

## 10. 质量门怎么决定能不能出报告

质量门是外部执行主体定稿前的强制反查，不是格式检查。

`06-质量门检查表` 至少包括：

```text
质量门ID
检查项
检查结果：通过 / 未通过 / 待确认
发现问题
回退环节
处理动作
复查结果
```

最低质量门包括：

- 画像字段是否完整；
- 知识路由是否覆盖地域、采购方式、品目、场景、章节；
- 必做动作是否全部执行；
- 逐章读取是否覆盖公告、需求、评分、合同、格式；
- 风险是否都有原文证据或明确缺失事实；
- `原文内容` 是否保持原文，不混入解释；
- 风险是否过度合并；
- 缺失类风险是否检查；
- 人员评分、供应商能力评分、方案承诺评分是否反查；
- 合同付款、验收、违约、模板错配是否反查；
- 风险数量异常偏低时是否触发反查；
- 待确认事项是否列明。

质量门不通过时，必须回退到画像、路由、动作执行或风险原子化环节，不得直接输出最终审查记录。

## 11. 报告输出具体是什么

外部执行主体最终至少输出两类正式结果：

| 输出 | 作用 |
| --- | --- |
| `07-AI审查记录` | 给业务审查人员阅读，列明画像、风险点、原文内容、问题说明和修改建议 |
| `08-运行记录` | 给系统审计和复现使用，说明读取了哪些知识、生成了哪些中间产物、执行了哪些动作 |

AI 审查记录不是运行日志。运行记录不是业务审查意见。二者不能混在一起。

### 11.1 AI 审查记录必须包含

```text
项目基本信息
文件画像摘要
知识路由摘要
动作执行摘要
风险点清单
已审查未列风险
待补证或待确认
质量门结论
文件位置
```

每条风险必须包含：

```text
风险标题
结论类型
风险等级
原文位置
原文内容
问题说明
来源动作ID
关联审查点
审查依据
修改建议
是否需要人工复核
```

### 11.2 运行记录必须包含

```text
执行边界
是否使用外部标注
必读知识清单
知识路由表
中间产物清单
文件画像
动作清单和执行状态
原文读取记录
原子风险清单摘要
质量门结果
未命中动作说明
待人工复核事项
模型调用或工具调用说明
是否修改知识库
```

## 12. 外部执行主体初始化成功标准

外部执行主体不是能打开文件就算接入成功，也不是能输出几个风险就算成功。

必须同时满足：

- 能确认输入是一份政府采购招标文件或采购文件；
- 能读取入口协议和必读知识；
- 能生成 `01-文件画像`；
- 能生成 `02-知识路由表`；
- 能生成 `03-动作清单`；
- 能生成 `04-动作执行记录`；
- 能生成 `05-原子风险清单`；
- 能生成 `06-质量门检查表`；
- 能生成 `07-AI审查记录`；
- 能生成 `08-运行记录`；
- 能逐章逐动作读取原文；
- 能区分存在型风险和缺失型风险；
- 能让每条风险关联来源动作、审查点和依据；
- 能执行质量门反查；
- 能说明未命中动作和待确认项。

如果只能输出一段总结、一个风险列表，或者只说“发现若干问题”，但没有画像、路由、动作、原子风险和质量门，就视为未完成外部执行主体使用线的初始化。

## 13. 执行主体最小提示词结构

外部执行主体可以按自己的技术实现调用模型，但给 AI 的任务信息至少应包含：

```text
你正在执行政府采购招标文件合规性审查。

必须遵守：
1. 只使用本项目 raw、wiki、tools 中的材料和明确引用的法规依据。
2. 不使用外部 V2、标准答案、人工批注反推风险。
3. 先建立文件画像，再知识路由，再生成动作清单。
4. 按动作逐章读取原文，记录命中、未命中、待确认、不适用。
5. 风险必须原子化，每条风险必须有原文证据或明确缺失事实。
6. 原文内容字段只能放招标文件原文，问题说明字段才写理由。
7. 输出前必须执行质量门。

本次必须读取：
- AGENTS.md
- wiki/index
- 外部执行主体招标文件审查指引
- 知识驱动审查执行规范
- 政府采购招标文件业务审查流水线
- 政府采购招标文件画像
- 知识分层与路由规则
- 政府采购逐章审查矩阵
- 风险审查点总览
- 风险原子化规则
- 质量门规则
- 审查记录模板
- AI调度运行记录模板

请生成并保留：
01-文件画像
02-知识路由表
03-动作清单
04-动作执行记录
05-原子风险清单
06-质量门检查表
07-AI审查记录
08-运行记录
```

如果文件画像命中某个品类，还必须加入命中品类动作协议。例如物业管理必须读取 [[wiki/70-审查协议/物业管理审查动作协议]]，并执行 `PROP-A01` 至 `PROP-A23`。

## 14. 和其他三条线的关系

外部执行主体使用线不是孤立存在的。

| 关系 | 说明 |
| --- | --- |
| 依赖知识生成管理线 | 读取法规、知识点、风险审查点、动作协议、模板和质量门 |
| 复现业务审查主流程线 | 按同一套画像、路由、动作、风险、质量门生成审查记录 |
| 接入审后调整和精确率提升线 | 业务人员调整后，可通过复盘和知识更新申请回写知识 |
| 反向约束知识系统 | 当画像字段、路由规则、动作协议、模板或质量门变化时，入口协议也要同步评估更新 |

因此，外部执行主体使用线的本质是：把本知识库从“人能看懂的知识”变成“外部执行器也能按步骤调用的审查能力”。
