## 1. SOP目标

本 SOP 用于把一个政府采购审查专题，从零建设为可被 AI、外部执行器和人工审查助理复用的 LLM Wiki 知识系统。

这里的“专题”可以是：

- 政府采购招标文件合规性审查；
- 政府采购四类专项检查；
- 某一采购品目审查，例如物业管理、家具、信息化设备、食材、安保、医疗设备；
- 某一风险专题审查，例如本地化限制、技术参数指向性、政府采购政策落实、评分办法合规性；
- 某一地域或平台专题审查，例如深圳政府采购文件审查。

本 SOP 的目标不是生成几篇说明文，而是形成一个完整闭环：

```text
原始材料
  -> 知识生成管理
  -> 动作化审查
  -> 审后复盘校准
  -> 外部执行主体复现
  -> 新知识回写
```

完成后的知识系统应满足：

- 人能看懂：新人可以理解专题背景、法规依据、风险类型和操作方法；
- AI 能执行：外部执行主体能按入口、路由、动作协议和质量门完成审查；
- 结果可追溯：每条风险都有原文证据、审查点、依据和判断说明；
- 知识可演进：人工调整和复盘可以回写为可复用知识；
- 专题可复制：同一方法可以迁移到新专题。

## 2. 核心原则

### 2.1 raw不可变

`raw/` 保存原始材料，不得覆盖、改写或加工替换。

所有知识加工都进入 `wiki/`。

### 2.2 AI审查和复盘校准分离

标准 AI 审查只能使用本项目 `raw/`、`wiki/`、`tools/` 中的材料和明确引用的官方依据。

外部批注、人工标注、标准答案或历史检查结果只能用于审后复盘，不得混入 AI 标准审查记录。

### 2.3 原文和判断分离

`原文内容` 必须是文件中的原文摘录或缺失事实说明。

风险理由、判断逻辑和修改建议必须放在对应字段中，不得用解释替代原文。

### 2.4 知识必须可驱动动作

稳定知识必须回答：

- 看哪里；
- 找什么；
- 怎么判断；
- 什么情况排除；
- 怎么输出；
- 怎么回写。

不能驱动动作的材料，只能作为背景或语料，不应直接作为审查规则。

### 2.5 先通用，再专题，再项目

知识建设顺序应为：

```text
全国通用规则
  -> 地域或平台规则
  -> 专题规则
  -> 品目或场景规则
  -> 项目经验
```

项目经验不得直接升级为稳定规则，必须经过复盘和知识更新申请。

## 3. 标准目录结构

新建或复制专题时，应沿用以下结构：

```text
raw/
  招标文件/ 或 专题材料/

wiki/
  00-入口/
  10-法规依据/
  15-行业基础/
  20-知识点/
  25-风险审查点/
  30-风险库/
  40-审查工作台/
  50-语料与摘录/
  60-提示词/
  70-审查协议/
  80-SOP/
  90-模板/

AGENTS.md
tools/wiki.py
ingest
query
lint
```

目录职责：

| 目录          | 职责         | 典型产物                |
| ----------- | ---------- | ------------------- |
| `raw/`      | 原始材料       | 招标文件、法规原文、截图、样本     |
| `00-入口/`    | 总纲和导航      | 首页、知识地图、外部执行指引      |
| `10-法规依据/`  | 官方依据       | 法律、规章、政策、标准、地方规则    |
| `15-行业基础/`  | 行业和专题画像    | 行业概览、专题背景、场景画像      |
| `20-知识点/`   | 判断规则和动作化知识 | 画像、逐章矩阵、动作化审查包      |
| `25-风险审查点/` | 稳定风险规则单元   | 风险审查点、触发信号、排除条件     |
| `30-风险库/`   | 跨专题风险模式    | 本地化、指向性参数、评分脱节      |
| `40-审查工作台/` | 项目过程产物     | 审查记录、运行记录、复盘、知识更新申请 |
| `50-语料与摘录/` | 来源笔记和典型条款  | 来源笔记、条款摘录、证据样本      |
| `60-提示词/`   | AI 操作提示    | 画像、抽取、审查、复核提示词      |
| `70-审查协议/`  | 可执行审查协议    | 动作协议、质量门、原子化规则      |
| `80-SOP/`   | 知识系统作业流程   | 建库、新品目、法规采集、复盘 SOP  |
| `90-模板/`    | 记录模板       | 审查记录、风险点、知识更新申请     |

## 4. 角色和职责

| 角色 | 主要职责 |
| --- | --- |
| 知识系统负责人 | 定义专题目标、验收标准、目录结构和权限边界 |
| 知识维护人 | 入库材料、抽取条款、编写知识点、风险审查点和 SOP |
| AI审查执行者 | 按知识路由、动作协议和质量门执行审查 |
| 业务复核人员 | 调整风险结论、确认误报漏报、提出知识更新申请 |
| 外部执行主体 | 读取本知识库并复现审查动作，不硬编码业务知识 |
| 法规复核人 | 核验法规、标准、地方规则和政策效力 |
| 品目专家 | 核验品目场景、行业惯例、合理需求和误报边界 |

## 5. 建设总流水线

标准建设流程如下：

```text
P0 目标定义
P1 工程初始化
P2 操作边界和协作协议
P3 行业和专题基础建模
P4 法规依据层建设
P5 知识点和风险审查点建设
P6 样本入库和语料抽取
P7 动作化审查设计
P8 项目样本审查跑通
P9 人工复盘和知识回写
P10 外部执行主体使用线
P11 SOP化和专题复制
P12 持续治理和版本演进
```

每一阶段都必须有输入、动作、输出和质量标准。

## 6. P0 目标定义

### 输入

- 用户或业务方提出的专题需求；
- 预期审查对象；
- 预期输出结果；
- 可用样本材料；
- 可用法规或政策依据。

### 动作

明确以下问题：

- 本专题审查什么；
- 不审查什么；
- 输出给谁看；
- 输出到哪里；
- 结果用于初审、复核、整改，还是专项检查报告；
- AI 可以使用哪些材料；
- 人工复核如何介入；
- 外部执行主体是否需要复现。

### 输出

建议形成：

- `wiki/00-入口/某专题建设纲领.md`
- `wiki/00-入口/某专题知识地图.md`

### 质量标准

目标定义必须写清：

- 审查对象；
- 风险范围；
- 证据要求；
- 输出格式；
- 禁止事项；
- 成功标准。

### 招标文件审查样例

本项目最初目标是：按照 Karpathy LLM Wiki + Obsidian 方式，建立政府采购行业招标文件合规审查知识点，使后续招标文件进入后，AI 能基于知识库识别风险点。

## 7. P1 工程初始化

### 输入

- 空目录或已有项目目录；
- Karpathy 风格 LLM Wiki 建设要求；
- Obsidian 可读 Markdown 要求。

### 动作

建立基础文件：

```text
raw/
wiki/
AGENTS.md
wiki/index.md
wiki/log.md
tools/wiki.py
ingest
query
lint
```

建立 wiki 分层目录：

```text
00-入口
10-法规依据
15-行业基础
20-知识点
25-风险审查点
30-风险库
40-审查工作台
50-语料与摘录
60-提示词
70-审查协议
80-SOP
90-模板
```

### 输出

- 可运行的 `./ingest`
- 可运行的 `./query`
- 可运行的 `./lint`
- 初始 `wiki/index.md`
- 初始 `wiki/log.md`

### 质量标准

- `./lint` 通过；
- 目录职责清楚；
- Obsidian 双链可用；
- `raw/` 和 `wiki/` 权限边界明确。

## 8. P2 操作边界和协作协议

### 输入

- 专题目标；
- 目录结构；
- 审查纪律。

### 动作

编写或更新 `AGENTS.md`。

必须规定：

- 不得修改 `raw/`；
- 标准 AI 审查不得读取外部答案；
- 原文内容必须保留原文；
- 风险必须有审查点和依据；
- 法律依据不确定时标记 `需进一步确认`；
- 新知识要回写；
- 重要工作写入 `wiki/log.md`。

### 输出

- `AGENTS.md`
- 必要时新增 `wiki/00-入口/LLM-Wiki工作法.md`

### 质量标准

- 新执行者能从 `AGENTS.md` 得知能做什么、不能做什么；
- 协作协议能约束 AI、人工和外部执行主体。

## 9. P3 行业和专题基础建模

### 输入

- 专题目标；
- 基础行业资料；
- 样本文件标题和目录；
- 业务人员对场景的初步说明。

### 动作

建立行业和专题画像：

- 行业概览；
- 法律政策体系；
- 参与主体；
- 业务流程；
- 文件结构；
- 审查对象；
- 证据链方法；
- 场景画像；
- 常见误报边界。

### 输出

建议页面：

```text
wiki/15-行业基础/某行业概览.md
wiki/15-行业基础/某专题背景.md
wiki/15-行业基础/某专题场景画像.md
wiki/15-行业基础/审查对象与证据链.md
```

### 质量标准

- 新人能读懂专题是什么；
- AI 能根据画像判断应该调用哪些知识；
- 场景画像只用于路由，不直接形成风险结论。

## 10. P4 法规依据层建设

### 输入

- 专题范围；
- 官方法规、政策、标准、地方规则；
- 已有法规索引。

### 动作

采集和整理官方依据：

- 法律；
- 行政法规；
- 部门规章；
- 规范性文件；
- 地方条例和实施细则；
- 政策清单；
- 国家标准、行业标准；
- 平台规则。

每个依据页应包含：

- 名称；
- 类型；
- 状态；
- 来源；
- 效力层级；
- 适用地域；
- 适用品目或专题；
- 审查用途；
- 关联审查点。

### 输出

```text
wiki/10-法规依据/某法规或政策.md
wiki/10-法规依据/某专题法规标准依据.md
```

### 质量标准

- 优先官方来源；
- 效力层级清楚；
- 适用范围清楚；
- 不确定内容标记 `待核` 或 `需进一步确认`；
- 不把样本经验当作法规依据。

## 11. P5 知识点和风险审查点建设

### 输入

- 法规依据；
- 行业画像；
- 样本风险表达；
- 人工经验。

### 动作

建立两类知识：

1. 知识点：审查判断框架。
2. 风险审查点：稳定风险规则单元。

知识点回答：

- 审查目标；
- 高频关注点；
- 判断框架；
- 输出口径。

风险审查点回答：

- 审查对象；
- 触发信号；
- 判断规则；
- 排除条件；
- 默认等级；
- 关联法规；
- 关联知识点；
- 输出口径。

### 输出

```text
wiki/20-知识点/某审查知识点.md
wiki/25-风险审查点/某风险审查点.md
wiki/25-风险审查点/风险审查点总览.md
```

### 质量标准

- 每个风险审查点能承接多个项目风险标题；
- 每个风险审查点有排除条件；
- 风险审查点不是项目个案复述；
- 能被知识路由和动作协议调用。

## 12. P6 样本入库和语料抽取

### 输入

- 原始招标文件或专题材料；
- `./ingest` 工具；
- 条款抽取提示词。

### 动作

对原始材料入库：

```bash
./ingest raw/招标文件/某品目/example.docx
```

抽取关键内容：

- 项目基本信息；
- 采购方式；
- 预算和最高限价；
- 资格条件；
- 政府采购政策；
- 采购需求；
- 技术参数或服务要求；
- 评分办法；
- 证明材料；
- 合同条款；
- 付款和验收；
- 疑似风险条款；
- 缺失项。

### 输出

```text
wiki/50-语料与摘录/来源笔记.md
wiki/50-语料与摘录/某专题典型条款摘录.md
```

### 质量标准

- 每个来源可追溯到 `raw/`；
- 原文摘录保留原文；
- 抽取不等于定性；
- 缺失项也记录；
- 更新 `wiki/index.md` 和 `wiki/log.md`。

## 13. P7 动作化审查设计

### 输入

- 行业画像；
- 法规依据；
- 知识点；
- 风险审查点；
- 样本条款。

### 动作

把知识加工成可执行流程：

```text
文件画像
  -> 知识路由
  -> 动作清单
  -> 逐动作执行
  -> 风险原子化
  -> 质量门
  -> 报告输出
```

必须建立：

- 文件画像规则；
- 知识分层与路由规则；
- 逐章审查矩阵；
- 专题或品目动作化审查包；
- 审查动作协议；
- 风险原子化规则；
- 质量门规则。

### 输出

```text
wiki/20-知识点/政府采购招标文件画像.md
wiki/20-知识点/知识分层与路由规则.md
wiki/20-知识点/政府采购逐章审查矩阵.md
wiki/20-知识点/某专题动作化审查包.md
wiki/70-审查协议/某专题审查动作协议.md
wiki/70-审查协议/风险原子化规则.md
wiki/70-审查协议/质量门规则.md
```

### 质量标准

- 每个动作有 ID；
- 每个动作有必读章节；
- 每个动作有触发信号；
- 每个动作有输出要求；
- 未命中动作也能记录；
- 质量门能反查漏动作。

## 14. P8 项目样本审查跑通

### 输入

- 一个真实样本文件；
- 已建立知识和动作协议；
- 审查记录模板；
- 运行记录模板。

### 动作

按标准流程执行：

1. 建立文件画像；
2. 路由知识；
3. 生成动作清单；
4. 逐动作阅读原文；
5. 识别风险和缺失项；
6. 按风险原子化规则拆分；
7. 执行质量门；
8. 输出审查记录；
9. 输出运行记录。

### 输出

```text
wiki/40-审查工作台/审查记录/某专题/xxx-审查记录.md
wiki/40-审查工作台/运行记录/某专题/xxx-AI调度运行记录.md
```

### 质量标准

每条风险至少包含：

- 风险标题；
- 结论类型；
- 风险等级；
- 原文位置；
- 原文内容；
- 问题说明；
- 关联审查点；
- 审查依据；
- 修改建议。

运行记录至少包含：

- 审查日期和具体时间；
- 输入文件；
- 读取知识；
- 动作清单；
- 工具调用或阅读过程；
- 质量门结果；
- 未命中动作说明。

## 15. P9 人工复盘和知识回写

### 输入

- AI 审查记录；
- 业务人员调整意见；
- 漏报、误报、争议项；
- 外部批注或标准答案。

### 动作

区分三类结果：

- 正确风险：保留并可作为样本；
- 漏报：分析为什么动作、风险点或质量门没有覆盖；
- 误报：分析排除条件、场景边界或依据是否不足。

形成：

- 人工调整复盘；
- 知识更新申请；
- 风险审查点补强；
- 动作协议补强；
- 质量门补强；
- 语料样本补充。

### 输出

```text
wiki/40-审查工作台/人工调整复盘/某专题/xxx-人工调整复盘.md
wiki/40-审查工作台/知识更新申请/某专题/xxx-知识更新申请.md
```

### 质量标准

- 复盘不直接覆盖 AI 审查记录；
- 可复用内容必须回写到知识层；
- 项目个案经验不能直接升级为通用规则；
- 回写后应能影响下一次审查。

## 16. P10 外部执行主体使用线

### 输入

- 已建立的知识库；
- 外部执行主体需求；
- 审查动作协议；
- 运行记录模板。

### 动作

为外部执行主体明确：

- 初始化读取顺序；
- 必读知识；
- 文件画像格式；
- 知识路由规则；
- 动作清单格式；
- 逐动作执行要求；
- 风险原子化规则；
- 质量门要求；
- 审查记录输出格式；
- 运行记录输出格式。

### 输出

```text
wiki/00-入口/外部执行主体招标文件审查指引.md
wiki/00-入口/外部执行主体使用线内部说明.md
wiki/70-审查协议/知识驱动审查执行规范.md
```

### 质量标准

- 外部执行主体不需要知道历史对话，也能找到入口；
- 外部执行主体不硬编码业务知识；
- 知识更新后，外部执行主体能通过读取 wiki 感知变化；
- 执行过程能留下运行记录。

## 17. P11 SOP化和专题复制

### 输入

- 已跑通的专题知识系统；
- 新专题需求；
- 本 SOP；
- 已有 SOP 和模板。

### 动作

将已跑通过程沉淀为 SOP：

- 总建设 SOP；
- 新品目知识包 SOP；
- 法规依据采集 SOP；
- 风险审查点新增与改造 SOP；
- 动作化审查包建设 SOP；
- 项目审查记录生成 SOP；
- 人工调整复盘与知识回写 SOP；
- 外部执行主体适配 SOP。

复制到新专题时，按以下方式替换：

```text
审查对象
法规依据
行业画像
风险审查点
动作协议
质量门
样本文件
输出模板
```

### 输出

```text
wiki/80-SOP/某专题知识系统建设SOP.md
```

### 质量标准

- 新专题能按 SOP 复建；
- 不依赖某次对话记忆；
- 不依赖某个特定执行者；
- 能通过 `./lint` 检查。

## 18. P12 持续治理和版本演进

### 输入

- 新法规；
- 新样本；
- 新审查结果；
- 人工复盘；
- 外部执行主体运行偏差。

### 动作

持续治理包括：

- 定期检查法规是否过期；
- 检查风险审查点是否重复、冲突或缺少排除条件；
- 检查动作协议是否可执行；
- 检查质量门是否覆盖高频漏报；
- 检查项目经验是否已回写；
- 检查外部执行主体指引是否与知识变化同步；
- 检查 index 和 log 是否完整。

### 输出

- 知识更新申请；
- SOP 修订；
- 风险审查点改造；
- 动作协议版本更新；
- 质量门更新；
- 阶段性收口报告。

### 质量标准

- 所有重要更新写入 `wiki/log.md`；
- 试运行知识有明确状态；
- 稳定知识有依据和复核；
- 废止或冲突知识不继续被路由调用。
