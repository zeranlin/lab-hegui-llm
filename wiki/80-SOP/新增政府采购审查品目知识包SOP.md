## 1. 目标

本 SOP 用于规范如何增加一个新的政府采购招标文件合规审查品目知识包。

新品目可以是家具、食材、安保、印刷、医疗设备、信息化设备、物业管理等。目标不是简单建立资料夹，而是形成一个能被 AI 或外部执行主体读取、路由、执行、反查和复盘的动作型知识包。

完成后的新品目知识包应能回答：

- 这是什么采购品目；
- 适用哪些法规、政策、标准和地方规则；
- 常见场景和高频风险是什么；
- 审查时应看哪些章节；
- 每个动作要找什么、怎么判断、怎么输出；
- 审查结束前如何反查漏项；
- 审查后如何通过人工复盘回写知识。

## 2. 输入材料

新增品目时，至少应准备：

- `raw/招标文件/某品目/` 下的原始招标文件；
- 已有政府采购通用法规和风险审查点；
- 该品目可能涉及的官方政策、标准、清单或监管规则；
- 已有相近品目的动作包、审查协议和质量门；
- 如有人工标注或外部批注，只能用于审后复盘，不得用于 AI 标准审查阶段反推风险。

## 4. 标准流水线

### 4.1 新品目立项

先判断该目录是否需要作为独立品目建设。

必须回答：

- 采购对象是什么；
- 属于货物、服务、工程还是混合采购；
- 是否已有相近品目可复用；
- 是否存在独立高频风险；
- 样本数量是否足够支撑试运行知识；
- 是否需要建立独立动作化审查包。

输出：

- 品目立项判断；
- 初步品目标签；
- 初步场景标签；
- 是否独立建包的结论。

完成标准：

- 能说明为什么它不是仅靠通用规则就能覆盖；
- 能说明它与既有品目之间的复用关系。

### 4.2 来源入库

对新目录下的原始文件建立来源笔记。

操作：

```bash
./ingest raw/招标文件/某品目/example.docx
```

要求：

- 不修改 `raw/` 原文件；
- 来源笔记保留来源路径、文件大小、sha256 和入库日期；
- 来源笔记初始状态可以是 `待抽取`；
- 更新 `wiki/index.md` 和 `wiki/log.md`。

完成标准：

- 每份原始文件都有来源笔记；
- `./lint` 不因新增来源笔记失败。

### 4.3 品目画像

建立该品目的行业基础页。

必须包含：

- 采购类型；
- 常见采购标的；
- 细分场景；
- 常见章节；
- 常见政策；
- 常见评分因素；
- 常见合同和履约问题；
- 常见误报边界。

输出：

- `wiki/15-行业基础/某品目采购背景.md`
- 更新 [[wiki/15-行业基础/政府采购专项场景画像]]

完成标准：

- 外部执行主体能仅通过画像判断是否调用该品目知识包；
- 能列出该品目的高频审查入口。

### 4.4 外部依据补齐

新品目不能只从样本文件总结，必须补齐官方依据。

应查找：

- 政府采购品目分类；
- 政府采购通用法规；
- 中小企业政策；
- 节能环保、进口产品、强制认证、绿色采购等政策；
- 国家标准、行业标准或强制性标准；
- 地方政府采购规则；
- 平台规则；
- 品目特有监管要求。

输出：

- `wiki/10-法规依据/某品目法规标准依据.md`

完成标准：

- 能区分法律依据、政策依据、标准依据和样本经验；
- 对未核验或不确定依据标记 `需进一步确认`；
- 不使用非官方材料作为唯一法律依据。

### 4.5 样本条款抽取

从样本文件中抽取品目共性条款，不急于形成风险结论。

抽取章节：

- 招标公告；
- 资格条件；
- 政府采购政策；
- 采购需求；
- 技术参数或服务要求；
- 评分办法；
- 样品、演示、踏勘或答辩；
- 证明材料；
- 合同、付款、验收和违约；
- 投标文件格式。

要求：

- 原文摘录保留原文，不用解释替代原文；
- 摘录要能追溯到具体文件、章节或条款；
- 缺失项也要记录，例如预算、所属行业、核心产品、合同空白。

输出：

- 来源笔记中的关键摘录；
- 必要时新增品目典型条款摘录页。

完成标准：

- 能从样本中归纳触发信号；
- 每类触发信号至少有原文样本支撑。

### 4.6 高频风险归纳

把样本条款和外部依据进行比对，归纳高频风险入口。

每个风险入口必须回答：

- 看哪里；
- 找什么；
- 为什么可能有风险；
- 什么时候不构成风险；
- 关联哪个法规、知识点或风险审查点；
- 输出时标题和原文内容如何写。

输出：

- 更新品目背景；
- 更新或新增 `wiki/25-风险审查点/`；
- 必要时更新 `wiki/30-风险库/`。

完成标准：

- 风险入口不是散点经验，而是能归入稳定审查点；
- 每个风险入口都有排除条件，降低误报。

### 4.7 动作化审查包

把品目知识转化为 AI 可执行动作。

动作化审查包应包含：

- 定位；
- 画像路由；
- 逐章调度；
- 高频风险动作卡；
- 输出规则；
- 当前语料来源；
- 新细分场景入库补充顺序。

输出：

- `wiki/20-知识点/某品目动作化审查包.md`

完成标准：

- 能指导执行主体从文件画像进入逐章审查；
- 能说明每类风险的看哪里、找什么、怎么判断、怎么输出。

### 4.8 审查动作协议

将动作化审查包进一步固化为动作任务。

每个动作必须包含：

```text
动作ID::
动作名称::
适用场景::
必读章节::
触发信号::
必须检查::
输出要求::
关联审查点::
原子化提示::
未命中也必须记录::
```

输出：

- `wiki/70-审查协议/某品目审查动作协议.md`

完成标准：

- 每个动作都可执行；
- 未命中也能被记录；
- 能与质量门一一对应；
- 外部执行主体可以按动作 ID 逐项执行。

### 4.9 质量门设计

质量门用于审查记录定稿前反查漏项。

每个新品目至少应建立：

- 画像质量门；
- 采购需求或技术参数质量门；
- 评分办法质量门；
- 证明材料质量门；
- 合同和验收质量门；
- 异常低风险数量反查。

输出：

- 更新 [[wiki/70-审查协议/质量门规则]]

完成标准：

- 质量门能反查本品目最容易漏掉的动作；
- 质量门能明确未通过时应回到哪个动作 ID。

### 4.10 知识路由接入

把新品目接入整个知识系统。

必须更新：

- [[wiki/20-知识点/知识分层与路由规则]]
- [[wiki/15-行业基础/政府采购专项场景画像]]
- [[wiki/25-风险审查点/风险审查点总览]]
- [[wiki/index]]
- [[wiki/log]]

必要时更新：

- [[wiki/00-入口/外部执行主体招标文件审查指引]]
- [[wiki/70-审查协议/知识驱动审查执行规范]]
- [[wiki/60-提示词/招标文件合规审查总提示词]]

完成标准：

- 文件画像命中新品目后，能自然路由到对应背景、依据、动作包、动作协议、风险审查点和质量门；
- 新页面均已进入索引；
- `./lint` 通过。

### 4.11 样本验证

至少选择 1 份新文件进行 AI 审查验证。

验证内容：

- 是否正确画像；
- 是否调用新品目动作包；
- 是否逐动作执行；
- 是否能输出风险点；
- 是否漏掉明显风险；
- 是否存在误报；
- 是否执行质量门；
- 审查记录是否符合模板。

输出：

- `wiki/40-审查工作台/审查记录/某品目/xxx-审查记录.md`
- `wiki/40-审查工作台/运行记录/某品目/xxx-AI调度运行记录.md`

完成标准：

- 至少有一份样本能证明新品目知识包可驱动审查；
- 运行记录能说明输入知识、动作清单、执行状态和质量门结果。

### 4.12 复盘回写

样本验证后，处理漏报、误报和人工调整。

回写路径：

| 复盘发现 | 回写位置 |
| --- | --- |
| 新法规或标准 | `wiki/10-法规依据/` |
| 新场景画像 | `wiki/15-行业基础/` |
| 新判断规则 | `wiki/25-风险审查点/` |
| 新审查动作 | `wiki/20-知识点/` 或 `wiki/70-审查协议/` |
| 新质量门 | `wiki/70-审查协议/质量门规则.md` |
| 新输出要求 | `wiki/90-模板/` 或 `wiki/60-提示词/` |
| 典型原文 | `wiki/50-语料与摘录/` |

完成标准：

- 漏报和误报不只停留在项目记录中；
- 可复用内容通过知识更新申请进入稳定知识；
- 下一次同品目审查能调用到更新后的知识。

## 5. 完成判定

一个新品目知识包完成试运行版，至少满足：

- 来源文件已入库；
- 品目背景已建立；
- 外部依据已补齐或标明待核；
- 高频风险已归纳；
- 动作化审查包已建立；
- 审查动作协议已建立；
- 质量门已接入；
- 路由、索引、日志已更新；
- `./lint` 通过；
- 至少有一份样本审查或明确列入待验证。

## 6. 禁止事项

- 不得修改或覆盖 `raw/` 原始文件。
- 不得用外部标准答案、人工批注或 V2 检查结果反推 AI 标准审查风险。
- 不得只凭样本文件中的采购人写法直接形成稳定规则。
- 不得只建立背景页而不建立动作协议和质量门。
- 不得新增无法追溯来源、无法执行、无法判断排除条件的风险审查点。
- 不得把项目经验直接升级为通用规则，必须经过复盘和知识更新申请。
